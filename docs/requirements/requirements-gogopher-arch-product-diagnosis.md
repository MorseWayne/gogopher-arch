# GoGopher Arch 产品现状与需求诊断

- 日期：2026-07-12
- 状态：现状诊断；其中“虚拟实习工作台作为唯一产品核心”的建议已被后续定位讨论修正
- 分析范围：产品定位、核心用户路径、信息架构、实际功能边界、视觉体验
- 不在本轮范围：业务代码修改、完整交互方案、视觉稿

> 后续确认的产品定位、核心用户和开放资源策略见 `requirements-gogopher-arch-product-positioning.md`。虚拟实习与开源项目实践将作为训练方式，而不是唯一产品定位。

## 结论摘要

GoGopher Arch 当前已经是一个可以运行、内容量可观、视觉统一的学习产品原型，但还不是一个闭环成立的“Go 后端实习成长平台”。

现在的核心矛盾不是颜色、圆角或 shadcn 组件选择，而是产品身份和实际主体验没有对齐：

- 定位文档把“虚拟实习模拟器”定义为产品外壳，把连续项目任务定义为内容骨架。
- 实际产品的内容重心是 13 章 Go 教材式课程。
- 实习任务只实现了 3 个静态任务，任务详情、代码编辑、运行反馈和验收没有形成同一页面内的完整循环。
- Dashboard 用静态演示进度和实现来源标签模拟学习状态，视觉上像产品，行为上仍是原型。
- README 与当前实现存在明显漂移，扩大了用户对产品能力的预期。

因此，“对整体产品设计不满意”很可能不是单纯的视觉不满意，而是用户能感觉到：页面很多、卡片很完整，但核心学习动作不够真实，也没有一个足够强的产品主角。

## 一、项目实际现状

### 1. 已经真实可用的能力

- 公开首页、学习总览、Go 基础课程、章节详情、任务详情 5 类主要页面已经接入路由。
- 13 章 Go 基础课程以 MDX 形式内置，包含学习目标、正文、现代 Go 说明、工程实践、常见坑、复盘问题和练习。
- 课程练习支持 CodeMirror 编辑、Go 高亮与补全、浏览器本地草稿、重置和运行。
- 前端可以通过 `POST /api/v1/execute` 把 Go 代码发送到 Gateway，再转发到 Sandbox Engine 执行 `go run`。
- 运行链路可以返回 stdout、stderr、exit code、状态和耗时。
- 当前前端生产构建通过，Go 包可以编译并通过 `go test ./...`。

### 2. 仍属于原型或静态演示的能力

- 没有账号、用户、真实学习记录、任务状态或服务端进度模型。
- Dashboard 的 6% 进度由章节数和任务数静态计算，不代表用户行为。
- Dashboard 的“已读第一章”和任务状态是预置展示，不由真实完成事件驱动。
- 实习任务目录只有 Day 1、Day 2、Day 3 三个任务，其中只有 Day 1 可操作，后两个锁定。
- 任务详情页代码只读；实际运行要跳回 Dashboard，并且运行的是预置起始代码，不是用户在任务页修改后的代码。
- 任务验收勾选和 2/4 进度根据预置任务状态计算，不是沙盒检查结果。
- “导师提示”是静态文案，没有任务检查器、测试运行器或 AI 服务。
- Gateway 业务接口只有执行代码和健康检查，没有内容、任务、进度、评分或用户 API。
- PostgreSQL 和 Redis 在部署链路里存在，但不参与当前核心学习流程。

### 3. 当前真实用户路径

```text
公开首页
├── Go 基础训练营
│   └── 章节详情
│       ├── 阅读长篇课程
│       └── 编辑练习代码 -> 本地保存 -> execute API -> 输出匹配
└── 学习总览
    ├── 静态推荐、静态进度、路线预告
    ├── 运行某个任务的预置起始代码 -> execute API
    └── 任务详情
        ├── 阅读 Brief、目标、小课和验收标准
        └── 跳回学习总览才能运行代码
```

课程路径已经具备“读、改、跑、看结果”的最小闭环；任务路径尚未具备“读任务、改代码、跑测试、根据反馈迭代、完成任务”的闭环。

## 二、产品设计问题

### P0：产品主角错位

原定位最有辨识度的部分是“虚拟 Go 后端团队的入职第一周”，但实际首页和课程入口把 13 章基础课程放在主路径，实习任务变成课程之后的附属入口。

这使产品退回到竞争最拥挤的形态：一个带在线运行器的 Go 教程。真正有区分度的“职场任务、连续项目、验收、导师反馈”反而最薄。

### P0：核心学习循环被拆散

设计文档要求任务卡、小课、编辑器、运行/测试、针对性反馈、复盘和成长记录组成一个循环。当前实现把这些动作拆在 MissionDetail 和 Dashboard 两个页面：

- 详情页负责理解任务，但不能编辑或运行。
- Dashboard 可以运行，但代码只读且上下文较弱。
- 运行结果不驱动验收项、解锁状态或下一步。
- 没有任务完成和复盘状态。

用户不是在“完成任务”，而是在“阅读任务说明并运行示例程序”。

### P0：产品承诺与实现漂移

README 把 Day 0 到 Day 5、数据库/事务、缓存、可观测性、部署可靠性全部标记为完成；当前前端只有 3 个实习任务，工程进阶仍明确显示为即将开放。

README 还描述了运行测试、任务反馈、任务后复盘等能力，但后端实际只有 `go run`，任务线没有测试模式和真实任务检查。

这种漂移会让设计显得“不可信”：不是页面不好看，而是页面、文案和行为在讲三个不同成熟度的产品。

### P1：Dashboard 暴露实现细节，缺少用户语义

`source: staticMock`、`source: localSession`、`source: derivedFromContent` 对开发验收有用，但不应该成为主界面信息。它们和“访客演示”“不代表账号级真实进度”等说明一起占据首屏，把产品注意力从“你下一步要完成什么”转向“哪些东西还没做”。

Dashboard 同时承担路线图、进度面板、章节入口、任务列表和沙盒，结果是信息完整但行动焦点不强。

### P1：课程体验信息密度高，但学习节奏弱

- 课程总览把 13 章都做成结构相同的长卡片，桌面端需要长距离扫描，章节之间缺少阶段分组和先后关系。
- 章节页同时存在全站侧栏、章节目录、正文、页内目录和验收 checklist，导航层级过多。
- 正文由大量 Card 分段，视觉整齐但阅读节奏被边框反复打断。
- 学习目标、现代生态、工程实践、常见坑、复盘和练习都被赋予近似权重，用户不容易判断“今天最重要的动作”。

### P1：视觉统一，但缺少产品性格

当前 Go 蓝、浅色 surface、深色终端和 shadcn 组件已经形成一致视觉系统。问题不在“不统一”，而在：

- 页面主要由 Badge、Card、Progress、Tabs 组成，像设计系统展示页。
- 首页用路线数量和“可运行”证明价值，缺少一个具体任务成果或真实工作瞬间。
- 任务页虽然有深色代码区，但整体仍是文档阅读布局，没有形成 IDE/工单工作台的紧张感和连续上下文。
- 大量解释性文案在替功能说话，使界面显得谨慎而不自信。

## 三、需求成熟度诊断

当前不是 RA0“没有问题定义”。项目已经明确了核心用户和差异化方向。主要停留在以下状态：

### RA2：需求仍然偏宽、缺少可验证结果

- 同时覆盖 Go 初学者、实习生、工程师和 AI 全栈开发者，导致第一版难以围绕一个用户结果优化。
- “具备 Go 后端实习岗位能力”还没有被拆成一组可以被产品验证的能力结果。
- “真实任务”“导师反馈”“项目制学习”有方向，但没有统一的完成定义。

### RA3：关键产品约束尚未锁定

定位文档自己留下了两个决定产品形态的问题：

- 实习任务究竟围绕哪个连续后端项目展开？
- 第一版使用一个连续代码库，还是统一故事线下的独立小练习？

这两个问题未解决，后续设计只好用静态任务卡和独立代码片段代替真实项目上下文。

## 四、建议锁定的需求层级

### Must：先让一个核心闭环真实成立

1. 核心用户只服务“正在准备第一份 Go 后端实习/初级岗位”的学习者。
2. 核心产品只承诺“完成一段可验证的虚拟入职任务线”。
3. 每个任务在同一工作区完成：读 Brief、看必要小课、编辑代码、运行测试/检查、获得反馈、完成验收、进入复盘。
4. 任务状态必须由用户行为和检查结果产生，即使第一版只保存在 localStorage，也不能用预置状态冒充进度。
5. 产品文案、README 和 UI 只承诺当前真实存在的能力。

### Should：让课程服务任务，而不是与任务竞争

1. Go 基础内容作为诊断后的补课路径，或任务内的 just-in-time 小课。
2. 13 章课程可以保留为知识库，但不再成为所有用户必须先走完的主线。
3. Dashboard 收窄为“继续当前任务”和“最近反馈”，路线图降级到次级页面。
4. 任务之间共享一个最小连续项目或稳定的团队背景，让用户积累上下文。

### Could：在闭环验证后增加

- 账号与云端进度同步。
- AI 导师或代码评审。
- 工程能力进阶路线。
- RAG、Agent 和 AI 全栈路线。
- 更复杂的知识地图、成就或社区能力。

## 五、推荐的产品方向

建议回到 2026-04-26 定位文档里最有价值、但后来被稀释的选择：

> GoGopher Arch 首先是“Go 后端虚拟实习工作台”，课程是任务所需的知识支持，不是产品本体。

这不是推翻现有成果：

- 13 章 MDX 内容可以转为知识库和任务前置学习资源。
- CodeMirror、localStorage 草稿和 execute API 可以直接复用到任务工作台。
- Mission Brief、验收标准和静态任务数据可以作为任务模型起点。
- shadcn 视觉系统和 App Shell 可以保留，但页面职责需要收窄。

真正需要重新设计的是信息架构和学习状态模型，不是重新换一套 UI 库。

## 六、已确认约束与未验证假设

### 已确认约束

- 当前前端是 React + Vite + Tailwind + shadcn/ui。
- 课程内容已经大量投入并采用 MDX，不能把它当作一次性废弃物。
- 沙盒当前只支持单文件 Go 程序的 `go run`。
- 当前没有账号、后端进度、任务评分和 AI 服务。
- 工作区已有其他未提交修改，本轮不触碰业务代码。

### 未验证假设

- 用户是否仍认可“虚拟实习模拟器”作为唯一主产品方向。
- 首个任务线是否必须使用连续代码库。
- 目标用户对长篇基础课程的需求强度，还是更偏好任务中补课。
- 第一版的成功指标应是任务完成率、学习留存，还是岗位能力提升。

## 七、建议的下一步

下一阶段先不要做视觉稿。先完成一份窄范围产品重设计 Brief，只回答四件事：

1. 用户进入产品时正在经历什么具体困境？
2. 第一个 30 分钟内必须完成什么可验证成果？
3. 一个任务从打开到完成的唯一主流程是什么？
4. 哪些现有页面、文案和路线必须降级或移除，才能让这个流程成为主角？

在这四项确认后，再做信息架构和首页、工作台、任务页的重设计，视觉方案才不会继续为不确定的产品边界服务。

## 八、验证记录

- `gitnexus analyze`：1,583 nodes、2,651 edges、34 clusters、63 flows；索引仅用于理解，生成的仓库指引文件已清理。
- 浏览器：检查首页、学习总览、课程总览、章节详情、任务详情和移动端任务页；页面无控制台错误。
- 沙盒：从 Dashboard 发起任务运行，`POST /api/v1/execute` 返回 HTTP 200。
- 前端：`npm run build` 通过。
- 后端：`go test ./...` 通过，但当前所有 Go 包均无测试文件。
