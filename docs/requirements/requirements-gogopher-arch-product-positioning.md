# GoGopher Arch 产品定位需求

- 日期：2026-07-12
- 状态：需求发现中，核心方向已确认，信息架构与功能规格待继续设计
- 输出类型：Problem Statement、Need Hierarchy、Constraint Inventory、Scope Definition
- 关联文档：`requirements-gogopher-arch-product-diagnosis.md`

## 一、核心用户

首个核心用户不是完全没有编程经验的初学者，而是具有以下特征的开发者：

- 已经掌握 C++、Java 或其他语言，有一定后端基础。
- 了解 Go 基础语法，但缺少 Go 的惯用写法、高阶机制和生产工程经验。
- 能阅读简单 Go 代码，却很难从零完成一个完整程序。
- 手写、调试、测试和独立拆解任务的能力较弱。
- 对 AI 时代是否还应投入基础能力训练感到困惑。
- 希望通过真实实践成长为合格乃至高级 Go 技术栈工程师。

当前最具体的代表用户就是项目创建者本人：从 C++ 转向 Go，具备后端概念基础，但严重缺乏 Go 实际开发和完整交付能力。

## 二、问题陈述

具有其他语言经验的 Go 转型开发者，通常可以快速看懂语法和教程，却不知道如何把零散知识组织成持续的工程成长路线。他们在以下方面存在断层：

1. **知识到产出的断层**：知道语法，但无法独立完成完整 Go 程序。
2. **基础到工程的断层**：不知道语言特性如何进入 API、数据库、并发、测试和生产系统。
3. **工程到架构的断层**：不知道何时、通过什么实践从实现功能成长为负责系统设计。
4. **学习资源到能力的断层**：互联网上资料丰富，但缺少可信筛选、前置关系、实践任务和掌握验证。
5. **AI 使用与基本功的断层**：AI 可以生成代码，但用户缺少判断、调试、解释和面试所需的独立能力。
6. **短期学会到长期保持的断层**：学过的语法、工具和工程方法会逐渐生疏，但传统课程通常只记录是否完成，不重新验证用户是否仍能独立提取、应用和迁移这些能力。

如果这个问题不被解决，用户会持续在教程、书籍、开源项目和 AI 生成代码之间跳转，获得大量“看过”的知识，却无法形成可证明的工程能力。

## 三、已确认的产品定位

> GoGopher Arch 是面向有编程基础开发者的 Go 工程能力成长平台。它通过分层能力图谱、真实开源项目、开放技术资源和可验证的工程任务，帮助用户从掌握 Go 基础，成长到能够独立交付生产系统，并逐步具备高级工程与架构设计能力。

产品核心不是课程目录、开源项目导航或虚拟实习中的任意一个，而是能力成长系统。

```text
能力图谱
├── 决定学习路线与前置关系
├── 编排自有课程与开放资源
├── 选择真实开源项目作为训练场
├── 生成分层工程任务
├── 提供无 AI 与 AI 协作两种训练模式
├── 记录能力证据、薄弱点和下一步
└── 持续维护、重新验证并强化已学能力
```

## 四、目标能力画像

### 合格 Go 工程师

能够独立完成一个生产级 Go 服务或模块，包括：

- 理解需求并拆分开发任务。
- 使用符合 Go 习惯的方式设计包、接口和错误处理。
- 开发 HTTP/RPC 接口、数据库访问和后台任务。
- 编写单元测试、集成测试和必要的故障用例。
- 使用日志、调试器和基础诊断工具定位问题。
- 构建、配置、容器化并运行服务。
- 阅读并修改中等规模的陌生 Go 仓库。

### 高级 Go 工程师

能够独立负责一个生产级 Go 服务或子系统，包括：

- 评估需求、约束和技术方案并说明取舍。
- 处理并发、性能、资源、可靠性和安全问题。
- 使用 profiling、tracing、race detector、fuzzing 等工具诊断复杂问题。
- 设计可维护的模块边界、数据流和演进方案。
- 处理线上故障、回滚、复盘和长期治理。
- 评审他人代码，拆分可审查变更，并推动团队代码健康。
- 快速理解大型开源项目的架构和核心技术，完成有质量的贡献。

### 架构设计能力

架构不是高级工程师之后突然出现的一门课程，而是逐步加深的能力：

- 基础阶段理解函数、类型、包和依赖边界。
- 应用阶段理解服务内部模块和数据边界。
- 生产阶段理解容量、故障、可观测性和可靠性。
- 高级阶段理解跨服务交互、一致性、复杂度和演进成本。
- 架构阶段能够对多个系统的边界、数据流、可靠性和长期演进负责。

## 五、能力成长结构

### 纵向阶段

```text
Go 语言基础
    ↓
独立应用开发
    ↓
生产级工程能力
    ↓
复杂系统与分布式能力
    ↓
高级工程师与架构设计
```

### 横向能力领域

- 语言、标准库与运行时。
- 编码、设计与测试。
- HTTP、RPC、数据库、缓存和消息系统。
- 并发、异步任务与资源管理。
- 日志、指标、追踪、调试与性能。
- 安全、构建、部署和可靠性。
- 分布式系统与架构设计。
- 代码评审、技术决策、协作与 AI 使用。

基础和高阶应用必须是一等公民。同一能力节点需要表达不同深度，而不是把基础和高阶拆成互不相干的课程。

M1 与 M2 的节点、依赖、毕业项目和现有课程迁移草案见 `requirements-gogopher-arch-m1-m2-capability-graph.md`。

## 六、三种学习入口

### 引导式路线

从前置能力开始，自底向上完成阶段目标，适合不知道下一步学什么的用户。

### 项目式路线

围绕经过选择和固定版本的真实开源项目完成运行、追踪、修改、测试、诊断和贡献任务。

### 系统拆解路线

从一个完整系统、架构问题或生产故障出发，自顶向下展开所需能力；发现基础缺口时，自动回到对应节点补齐。

三种入口共享同一能力图谱和掌握记录，不能成为三套相互重复的内容。

## 七、统一学习闭环

每个能力节点应根据难度组合以下活动：

1. **原理**：说明概念、语义、边界和常见误区。
2. **示范**：展示完整的思考过程和经过验证的实现。
3. **补全**：从部分完成的代码过渡到独立解决问题。
4. **手写**：在限制 AI 的情况下完成最小实现和口头解释。
5. **实验**：主动制造错误、竞争、超时、性能或资源问题并观察结果。
6. **源码**：在标准库或开源项目中追踪真实实现。
7. **工程任务**：修改功能、补测试、修复故障或完成设计。
8. **验证**：通过代码、测试、解释、诊断和方案评审证明掌握。
9. **AI 协作**：用 AI 扩展任务规模，但由用户负责审查、验证和最终解释。

## 八、能力维护系统

能力维护不是课程完成后的附加复习功能，而是与能力图谱、真实项目训练并列的产品核心。产品需要同时回答三个问题：用户应该学什么、用户是否真正会做、用户现在是否仍然会做。

### 动态能力状态

能力掌握不能建模为永久布尔值。每个能力节点维护可重新验证的证据状态：

```text
学习中 → 已练习 → 已验证 → 稳定
                         ↓
                  待复习 → 生疏 → 重新验证
```

状态表达的是当前证据强度和新鲜度，不声称精确测量人的记忆。每个节点至少记录：

- 最近一次独立验证和 AI 辅助应用的时间。
- 作答速度、尝试次数、提示依赖和典型错误。
- 已使用过的项目、问题类型和上下文。
- 是否能解释原因、诊断失败并迁移到陌生场景。
- 当前证据强度、待补薄弱点和下一次维护时间。

独立完成证据与 AI 辅助证据必须分开。查阅答案或由 AI 生成后完成任务，不能自动刷新独立掌握状态。

### 分类型维护任务

不同能力使用不同的重新验证方式，不能全部退化成闪卡：

| 能力类型 | 主要维护方式 |
|---|---|
| 语法、API、命令 | 无提示回忆、短问题、代码补全 |
| 编码熟练度 | 从空文件手写小程序、函数或测试 |
| 原理与心智模型 | 预测行为、解释原因、复现边界条件 |
| 调试与诊断 | 根据失败测试、日志、trace 或 profile 定位问题 |
| 工程能力 | 在不同项目或约束下重新实现、改造和验证 |
| 架构能力 | 比较方案、说明权衡并应对约束变化 |

### 自适应间隔与重新学习

- 维护时间由能力类型、目标保持时间、历史表现、提示依赖和迁移结果共同决定，不采用对所有技能相同的固定周期。
- 答错、耗时过长或依赖提示时缩短重新验证间隔；在陌生场景中独立完成后才延长间隔。
- 维护任务遵循“先独立提取，再获得反馈，经过间隔后重新正确完成”的循环。
- 第一版可以使用保守的启发式调度，但必须保存足够证据，以便后续调整算法。

### 螺旋项目与交错练习

旧能力必须自然进入后续项目，而不是只出现在单独的复习页面。一个典型工程任务应组合一个当前新能力、若干历史能力和一个陌生约束。

例如 `context` 能力可以依次出现在：基础取消与超时、HTTP 请求取消、worker 生命周期、跨服务 deadline 传播，以及系统级超时、重试和降级设计中。用户面对的是复杂度逐渐增加的新问题，而不是机械重复原题。

### 能力维护节奏

- **日常维护**：短回忆、手写、代码重建或小型调试任务。
- **每周检查**：限制 AI 的综合验证，覆盖近期学习与历史薄弱能力。
- **里程碑验证**：在陌生项目或新约束下完成迁移挑战。
- **项目内复现**：后续任务主动调用已经学过但需要巩固的前置能力。

产品进度应展示“稳定、待复习、生疏、迁移不足”等信息，而不是只展示章节完成百分比。用户可以继续探索高阶内容，但关键前置能力过期时，系统需要生成明确的能力维护计划。

## 九、产品功能结构

产品不按照课程、题库、资源、AI 和项目分别堆叠孤立模块，而应围绕用户的能力成长流程组织。能力节点、训练过程和能力证据是所有入口共享的底层对象。

### 今日

用户每天进入产品后的默认行动入口，优先回答“我今天应该做什么”，而不是展示大量内容推荐。

- 一个当前主任务。
- 到期的能力维护任务。
- 当前项目进度。
- 最近暴露的薄弱点。
- 本周独立训练目标。

### 成长路线

能力图谱面向用户的主要视图，展示阶段、领域、前置依赖、当前状态、下一里程碑，以及能力在真实项目中的使用位置。

### 统一训练工作台

无论用户从引导式路线、开源项目还是系统拆解进入，最终都在同一工作台完成原理、示范、补全、手写、实验、源码、工程任务和验证。

工作台根据训练目的逐渐撤去帮助：

- **引导模式**：提供完整讲解、示范和步骤。
- **练习模式**：只提供约束、工具和分级提示。
- **验证模式**：限制 AI 和答案，只允许任务规定的必要资料。

### 开源项目实验室

把经过评估并固定版本的真实仓库转化为可重复的训练环境。每个训练包至少包含：

- 项目问题域、适用场景和技术价值。
- 架构概览、核心执行链路和推荐阅读路径。
- 可重复的本地运行、测试和调试方法。
- 与能力图谱的映射。
- 从局部修改、测试、故障诊断到系统设计的任务序列。
- 真实 Issue、PR 和设计讨论，以及可选的贡献出口。

### 能力档案

保存能够支撑能力判断的工程证据，而不是只展示积分和证书：

- 独立完成与 AI 辅助完成的代码和任务。
- 测试、调试、性能分析和故障处理记录。
- 项目修改、代码评审和架构决策。
- 稳定、待维护、生疏和迁移不足的能力。
- 可以对外展示的工程作品与成长记录。

### 嵌入式资源与 AI

开放资源和 AI 不作为孤立的一级学习模块。资源需要嵌入能力节点和任务，说明使用时机、阅读目标和完成后的验证；AI 需要嵌入训练工作台，在用户先尝试后提供诊断、分级提示、反馈和变式任务。

```text
今日任务
   ↓
成长路线 ────── 开源项目
   ↓               ↓
      统一训练工作台
              ↓
          能力证据
              ↓
        能力维护与下一步
```

## 十、核心用户首程

首个核心体验覆盖用户第一次进入产品，到完成 M1“Go 编程基础”里程碑。目标不是尽快展示内容数量，而是尽快让用户开始编写完整程序，并建立第一组可信能力证据。

### 目标与学习契约

用户首次进入时只需要说明技术背景、Go 经验、可投入时间、当前目标，以及是否接受限制 AI 的独立训练。系统据此生成当前学习契约，例如：脱离教程和 AI，独立完成一个结构清晰、包含测试并可以构建运行的 Go 程序。

### 实作诊断

诊断以一次可完成的训练为主，不依赖用户自评：

1. 阅读 Go 代码并预测行为。
2. 从空白开始实现小功能。
3. 为已有实现补充测试。
4. 根据失败信息定位错误。
5. 解释设计和错误处理方式。
6. 可选使用 AI 完成另一任务，验证审查和纠错能力。

结果分别表达概念理解、代码阅读、提示下完成、独立手写、问题诊断和跨场景迁移能力。针对其他语言转 Go 的用户，还应识别不符合 Go 习惯的语言迁移模式。

### 能力基线与补缺路线

系统根据行为证据生成能力基线，跳过已经证明掌握的内容；对“看懂但写不出”的能力安排示例渐隐和手写训练；对完全缺失的能力提供完整教学；并尽快把薄弱能力放进完整程序使用。

### 第一个完整程序

首个主线作品应是真实可运行的小型工具，而不是互不关联的语法题。初步建议使用 `gocheck` 服务状态检查工具作为内容原型：从配置读取地址，检查 HTTP 服务状态，并输出终端报告和 JSON 结果。

该项目可逐步承载模块初始化、包与类型、集合、配置、文件与 HTTP I/O、错误处理、命令行、表格驱动测试、日志、调试、构建，以及后续的并发、超时与取消。

同一项目逐步撤去帮助：

1. 跟随示范完成最小版本。
2. 只根据需求独立增加功能。
3. 从空目录完成一个结构不同的变式工具。

只有后续独立完成部分形成强独立能力证据。

### 日常学习闭环

```text
维护到期的旧能力
        ↓
推进一个当前项目任务
        ↓
提交代码、测试与解释
        ↓
分析错误和提示依赖
        ↓
更新能力证据与下一项任务
```

困难时依次提供问题澄清、能力定位、引导问题、接口或伪代码、局部示例和完整参考实现。提示越深入，当前任务形成的独立能力证据越弱，系统需要在后续安排重新验证，但不以此惩罚用户。

### M1 里程碑验证

M1 要求用户能够从空目录初始化项目，合理拆分包和函数，使用标准库完成输入、处理和输出，正确处理错误，编写有效测试，使用工具定位问题，构建可执行程序，并解释关键设计决定。

验证由无 AI 独立任务和 AI 协作任务组成，分别证明基本功与现代工程协作能力，两类证据不能互相替代。完成后自然进入 HTTP API、数据库、业务建模和真实开源项目训练。

## 十一、里程碑毕业标准

每个里程碑都必须通过四类验证：限制 AI 的独立任务、AI 协作任务、陌生上下文中的迁移任务，以及间隔一段时间后的延迟复验。毕业不使用简单平均分；关键前置能力仍处于生疏或未验证状态时，不能标记为稳定毕业。

### M1：Go 编程基础

用户需要从空目录独立完成一个真实可用的小型程序，包含合理的包结构、错误处理、单元测试、构建产物和使用说明，并能够解释 Go 与原有语言思维方式的主要差异。

毕业含义：从“能够看懂 Go”成长为“能够独立写出完整 Go 程序”。

### M2：Go 后端开发

用户需要独立交付一个包含 HTTP API、数据库与迁移、配置、日志、错误响应、单元与集成测试、基础认证或权限控制、后台任务或外部调用，并可容器化运行的后端服务。

关键证据包括需求拆分、业务与数据建模、API 与事务边界、`context` 传播、超时和输入处理、可测试模块设计，以及阅读和修改中等规模 Go 应用项目的能力。

毕业含义：从“会写程序”成长为“能够独立交付后端服务”。

### M3：生产工程能力

用户需要把 M2 服务部署并稳定运行，增加日志、指标、追踪和健康检查，完成压测与 profiling，处理超时、泄漏、竞争和依赖故障，并建立 CI、发布、回滚、备份和故障复盘流程。

关键证据包括 race detector、pprof、trace、fuzzing 等工具的实际使用，资源生命周期、容量性能、基础 SLI/SLO、重试限流降级恢复、安全与依赖风险分析，以及基于证据进行故障定位。

毕业含义：达到合格 Go 工程师标准，能够对一个生产服务负责。

### M4：复杂系统能力

用户需要深入一个大型 Go 开源项目，追踪核心执行链路，完成非平凡修改或故障修复，评估性能、兼容性和升级风险，完成分布式系统实验、代码评审和技术方案评审。

关键证据包括陌生仓库建模、复杂并发和异步资源管理、消息与缓存、一致性与故障模型、跨模块影响分析，以及拆分可审查、可回滚变更的能力。

毕业含义：进入高级 Go 工程师能力区间，能够负责复杂子系统。真实开源贡献可以自然发生，但不是强制毕业条件。

### M5：高级工程与架构设计

用户需要针对现实问题编写完整 RFC，设计系统边界、数据流和故障处理，分析容量、成本、可靠性与安全，制定渐进迁移、兼容和回滚方案，并使用原型或实验验证关键假设。

关键证据包括识别真实约束、比较方案长期成本、处理一致性与可用性权衡、设计可观测和可演进系统，以及在架构质询和约束变化后修订方案的能力。

毕业含义：从高级实现者成长为能够负责系统边界、技术决策和长期演进的工程师。

## 十二、第一版产品边界

第一版采用“完整地图、纵向打穿”的范围策略：

- 展示 M1 至 M5 的完整能力图谱与毕业标准。
- 完整实现 M1 Go 编程基础闭环。
- 完整实现 M2 Go 后端开发闭环。
- 在 M3 实现一条生产强化纵向样板。
- 接入一个固定版本、可重复运行的真实开源项目训练包。
- M4、M5 先提供清晰路线和少量代表性挑战，不伪装为完整内容。

M3 样板继续改造 M2 服务，使其具备可观测性、压测、故障演练、部署和回滚能力。第一版核心承诺是：

> M1、M2 完整闭环，加一条 M3 生产强化样板和一个贯穿式开源项目训练包。

## 十三、开放资源策略

### 核心原则

GoGopher Arch 不应闭门重新编写所有知识，也不能退化成链接目录。

平台负责：

- 判断一个能力节点需要什么知识和实践。
- 从可信开放资源中选择适合的材料。
- 说明为什么此时使用这个资源、应关注什么。
- 把知识转化为练习、项目任务和能力验证。
- 保留来源、许可证、版本和审校记录。

### 资源分层

#### 权威知识源

- Go 官方文档、语言规范、博客、标准库源码和工具文档。
- 项目官方设计文档、维护者文档、Issue、PR 和发布记录。
- 大学课程的官方讲义、论文、实验说明和考试材料。

#### 结构化教材与开放书籍

- 本地 `gopl-zh.github.com`，用于经典语言与标准库主线。
- Go 101，用于语法语义、运行时和细节深挖。
- Learn Go with Tests，用于测试驱动、行为设计和渐进练习方法。
- Google SRE 在线书籍与工作手册，用于生产工程和可靠性。
- MIT 6.5840，用于分布式系统论文、实验和设计训练。

#### 真实工程训练场

- 第一版应用工程项目：Miniflux v2.3.2，固定 commit `51f2e0d8199ea8fa305081f6e175bba64b0ef94b`，贯穿 M2 与 M3。
- 网络与插件架构候选：Caddy。
- 可观测性与时序系统候选：Prometheus。
- 分布式一致性候选：etcd。

后续项目仍是候选，不代表已经进入产品范围。项目必须按学习价值、规模、构建成本、文档、测试、许可证、活跃度和任务可维护性进行评估。Miniflux 的具体验证结果和训练包要求见 `requirements-gogopher-arch-miniflux-training-pack.md`。

#### 学习方法证据

- 掌握学习：达到可验证标准后再进入依赖它的能力节点。
- 示例渐隐：从完整示范、代码补全逐步过渡到独立实现。
- 检索练习：要求用户脱离材料回忆、解释和手写关键内容。
- 认知学徒制：展示专家如何阅读大型仓库、定位问题和做取舍，然后逐步撤去指导。
- 真实项目实践：使用真实代码库和真实约束训练隐性工程能力。

### 资源使用模式

每个资源必须选择明确的使用方式：

1. **事实校准**：只用于验证技术准确性，由平台重新组织解释。
2. **推荐阅读**：用户直接阅读原始材料，平台提供阅读目标和前后任务。
3. **许可改编**：在许可证允许时改编为站内教材或练习，并保留署名。
4. **项目训练**：固定仓库版本和代码位置，围绕真实源码设计原创任务。
5. **方法借鉴**：吸收教学结构，不复制受版权保护的正文和答案。

“可免费阅读”不等于“可以复制、改编或再发布”。所有资源在进入产品前必须完成许可证判断。

### 资源登记信息

每个资源至少记录：

- 标题、作者/组织、URL 或仓库地址。
- 资源类型和承担的教学角色。
- 对应能力节点、阶段和前置要求。
- 使用模式：校准、阅读、改编、训练或方法借鉴。
- 许可证、署名要求和禁止事项。
- 适用 Go 版本、项目 commit/tag 和最后审校时间。
- 语言、预计学习时间和内容难度。
- 已知争议、过时风险和替代资源。

## 十四、资源准入流程

```text
发现资源
  ↓
权威性、许可证、时效性与教学价值评估
  ↓
映射到能力节点和学习阶段
  ↓
选择使用模式
  ↓
设计阅读目标、练习或项目任务
  ↓
技术审校与学习验证
  ↓
发布并定期检查更新
```

资源质量优先级：

1. 官方规范、文档和源码。
2. 维护良好的项目官方材料。
3. 有明确作者、版本和审校记录的开放教材。
4. 经过同行评审或有可靠实践证据的课程与论文。
5. 社区文章和视频，只作为补充解释，不承担关键技术定义。

## 十五、许可证与使用边界

- Go 官网大部分内容采用 CC BY 4.0，代码采用 BSD，可在遵循署名和许可条件时使用。
- 本地 gopl-zh 仓库代码采用 BSD 风格许可，其项目说明标注正文采用 CC BY 3.0；改编时需要保留署名和来源。
- Learn Go with Tests 使用 MIT License，可作为练习与教学方法的重要开放来源。
- Google SRE 在线书籍可免费阅读，但部分内容采用 CC BY-NC-ND；应以推荐阅读和方法借鉴为主，不直接改编正文。
- MIT 6.5840 公开课程强调个人完成实验、理解并解释代码，并禁止公开实验答案；平台可以借鉴课程结构、引用材料或设计原创实验，不应发布课程解答。
- Go 101 当前按免费阅读资源处理；在许可证确认前不复制或改编正文。

本节不是法律意见。任何批量内容接入都需要再次核对资源当时的许可证原文。

## 十六、AI 使用原则

AI 是贯穿各阶段的协作工具，不是单独的最终赛道，也不能替代能力验证。

- 无 AI 模式：用于手写、面试、基础理解和独立诊断验证。
- AI 协作模式：用于仓库探索、方案比较、代码生成和大规模任务。
- 用户必须能解释 AI 产出、验证测试、发现错误并承担最终决策。
- 项目应记录哪些能力证据来自独立完成，哪些来自 AI 协作。

## 十七、Need Hierarchy

### Must

- 统一、可解释的 Go 工程能力图谱。
- Go 基础与高阶工程能力具有同等完整的学习与验证设计。
- 自底向上与自顶向下路线共享能力节点。
- 开放资源具有来源、许可证、版本和能力映射。
- 学习结果通过代码、测试、解释、诊断和设计证明。
- 真实开源项目成为工程训练载体，但不替代能力图谱。
- AI 使用和独立完成有清晰边界。
- 能力掌握是可衰减、可维护和可重新验证的动态证据，而不是永久完成状态。
- 通过检索、手写、间隔重学、螺旋项目和迁移任务保持长期能力。
- 今日、成长路线、统一训练工作台、开源项目实验室和能力档案共享同一套能力与证据数据。

### Should

- 入门诊断与个性化补缺路线。
- 固定版本的开源项目训练包。
- 示例渐隐和分类型掌握门槛。
- 根据表现、技能类型和目标保持时间进行自适应维护调度。
- 资源过期、项目变更和许可证变化检查。

### Could

- 真实开源贡献协作。
- 导师、同伴评审和社区学习。
- AI 代码评审和个性化讲解。
- 岗位画像、面试路线和企业能力标准映射。

### Won't Yet

- 覆盖所有 Go 应用方向和所有开源项目。
- 镜像或复制所有外部教程与书籍。
- 用课程完成度冒充工程能力。
- 让 AI 自动判定用户已经具备高级工程或架构能力。

## 十八、已确认约束与待确认问题

### 已确认

- 核心目标是培养合格乃至高级 Go 技术栈工程师。
- Go 基础和高阶应用都不可缺少。
- 开源项目是重要训练场，但贡献本身不是最终目标。
- 产品采用能力图谱主导、课程与项目双轮驱动的方向。
- 必须充分利用开放资源和成熟学习方法，避免闭门造车。
- 能力维护系统是一等核心能力，必须解决学后遗忘、手写生疏和跨场景迁移不足的问题。
- 产品以用户成长流程组织功能，不再把课程、题库、资源、AI 和项目建设成相互割裂的进度系统。
- 首次用户旅程以实作诊断开始，并尽快引导用户完成一个可运行、可测试、可构建的完整 Go 程序。
- 五个里程碑分别以完整程序、后端服务、生产服务、复杂子系统和架构决策作为毕业产出。
- 第一版采用 M1、M2 完整闭环，加 M3 生产强化样板和一个贯穿式开源项目训练包的范围。
- 第一版开源项目训练包固定 Miniflux v2.3.2 commit `51f2e0d8199ea8fa305081f6e175bba64b0ef94b`，使用可重复环境、本地 fixture 和分层测试。
- M1、M2 已拆为 14 个基础节点和 16 个后端节点，分别以 `gocheck` 与 `gocheck-hub` 作为内容原型，并通过 Miniflux 验证陌生项目迁移。

### 待确认

- Miniflux 首批任务的最终顺序、训练 patch 管理方式和目标用户试学结果。
- 诊断、掌握门槛、证据强度和维护调度的具体评分方式。
- 外部资源直接面向用户的展示方式。
- `gocheck` 与 `gocheck-hub` 的详细任务规格、试学结果和最终名称。
