# 规范化不是“顺手排个序”

配置进入系统后，后续逻辑希望面对的是一组有效、稳定、不会意外改变调用方数据的 target。`Normalize` 的职责因此包含三个部分：验证输入、生成规范结果、保持可预测的输出顺序。

## 先定义有效，再谈稳定

| 关注点 | 要回答的问题 | 常见风险 |
|---|---|---|
| 完整性 | 列表和关键字段是否为空？ | 无意义配置继续流入下游 |
| 合法性 | URL scheme、超时等值是否符合契约？ | 运行时才暴露配置错误 |
| 稳定性 | 相同集合是否总得到相同顺序？ | 输出 diff 和测试结果来回变化 |
| 副作用 | 规范化是否修改了调用方传入的 slice？ | 调用方在函数返回后看到数据被重排 |

验证应发生在输出形成之前。排序也应作用在结果副本上，而不是悄悄改变输入集合。

## 把失败条件拆开

不要用一个复杂分支同时处理所有非法输入。先列出每条输入约束，再让每个检查只回答一个问题。这样错误更容易定位，后续补测试时也能明确每个 case 在保护什么行为。

## 动手顺序

1. 阅读 `Target` 字段和公开测试，写下输入契约；
2. 先处理空集合和非法字段，让错误在边界处返回；
3. 为有效输入创建独立结果，再建立稳定顺序；
4. 运行 Test，并检查原始输入是否仍保持原顺序。

这项练习不要求依赖 JSON 编解码细节；重点是把外部数据转成稳定的内部表示。

## 完成后复盘

- 为什么“结果有序”不等于“可以原地排序输入”？
- 验证与排序的先后顺序会影响哪些错误表现？
- 如果明天新增一个字段约束，你会把检查放在哪里？
