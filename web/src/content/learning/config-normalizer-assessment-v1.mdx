# 把四项能力组合成一个命令

这次评估不再逐步指定修改点。你需要把工具链使用、错误处理、配置验证和测试设计组合成一个可以从命令行运行的 `checkcfg`。

## 先建立端到端契约

从使用者视角，数据会经过四个边界：

1. 命令行解析 `-config` 并决定失败时的 stderr 与退出状态；
2. `Load` 打开并解码指定文件，同时保留可判断的底层错误；
3. `Normalize` 拒绝非法 target，并产生稳定顺序；
4. 测试覆盖成功和失败行为，工具链检查整个 module。

先让这些边界各自职责清楚，再连接数据流。把所有工作都塞进 `main` 会让错误契约和测试边界变得模糊。

## 公开信息与独立判断

README、starter 文件和公开测试都是任务契约的一部分。它们告诉你输入输出和可观察行为，但不会列出所有验收样例。你的实现需要覆盖规则本身，而不是只让一个示例通过。

> 隐藏检查用于确认实现能推广到未展示的同类输入。不要猜测试名称；回到任务契约检查每条边界。

## 建议的工作节奏

1. 阅读 README、文件结构和公开测试，写下四个边界的完成条件；
2. 先让 Build 通过，再用 Test 推进可观察行为；
3. 为成功路径和至少两类失败路径补充自己的测试；
4. 运行 Vet，处理静态可疑写法；
5. 最后从命令入口重新走一遍成功与失败数据流，再提交评估。

提交后，平台会把公开反馈、未公开检查和你的完成小结合并成能力结果。运行成功只说明当前动作完成，最终结果以评估状态为准。

## 提交前自检

- 缺少参数、读取失败和非法配置是否都明确失败？
- 错误是否写到正确的输出通道，并保留底层原因？
- 有效 target 是否稳定排序，输入边界是否被验证？
- 自己新增的测试是否覆盖成功与不同类型的失败？
