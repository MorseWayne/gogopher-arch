# Build、Test、Vet：先知道工具在回答什么

写 Go 程序时，工具链不是最后才运行的一道闸门，而是一组逐步缩小问题范围的反馈工具。这节练习先建立最小循环：**编译、验证行为、检查可疑写法，然后解释你观察到的结果。**

## 三个命令，三个不同问题

| 动作 | 它回答的问题 | 失败时先看什么 |
|---|---|---|
| Build | 所有包能否完成编译和链接？ | 第一条编译错误、文件与行号 |
| Test | 已声明的行为是否仍满足测试？ | 第一个失败测试及其期望值与实际值 |
| Vet | 代码中是否存在编译器允许、但很可能写错的模式？ | 检查器给出的可疑位置与原因 |

Build 成功不代表程序行为正确；Test 通过也不代表没有静态可疑写法。三者是互补关系，不是谁替代谁。

## 为什么从第一条有效错误开始

一处语法或类型错误经常会引出很多后续错误。最后一行通常只是命令退出摘要，真正的原因更接近输出顶部。推荐按这个顺序阅读：

1. 找到第一个失败的阶段；
2. 找到第一条带文件与行号的错误；
3. 先修复这一处，再重新运行同一个动作；
4. 只有当前阶段通过后，再进入下一层检查。

> 工具返回非零退出码，通常说明代码或测试没有通过当前检查；如果平台提示运行环境中断或超时，可以重试，不要把它误判成代码错误。

## 现在动手

进入练习后依次运行 Build、Test、Vet。这个工作区已经足够小，因此你可以把注意力放在每个动作的输出和职责上。最后在“完成小结”中回答：

- Build、Test、Vet 分别验证什么？
- 如果某个动作失败，你会先检查哪条信息？

不需要背命令定义。能根据反馈选择下一步，才是这节课真正要建立的能力。
