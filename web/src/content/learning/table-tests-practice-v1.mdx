# 让失败输出直接说清行为

单个示例只能证明一条路径。表格驱动测试把一组输入、期望和行为名称放在一起，适合验证同一个函数在正常值、边界值和非法值上的契约。

## 一个 case 只表达一个行为

一张清晰的测试表通常包含：

- 能在失败输出中说明场景的 `name`；
- 当前场景的输入；
- 期望的结果或是否应报错；
- 一段对所有 case 共用的执行与断言逻辑。

case 名称应描述行为，而不是编号。`empty input is rejected` 比 `case 2` 更能帮助你在 CI 日志里直接定位问题。

## 正常、边界、非法

| 类型 | 这次可观察的行为 |
|---|---|
| 正常值 | 去除首尾空白并统一大小写 |
| 边界值 | 已规范化的值保持稳定 |
| 非法值 | 只有空白的名称返回错误 |

表格驱动不是为了减少行数，而是让同一份契约可以持续增加样例，同时保持失败信息清楚。

## 动手顺序

1. 保留对 `NormalizeName` 外部行为的关注，不检查内部实现；
2. 把现有示例迁入带名称的 case 表；
3. 增加至少三个能区分行为的 case，并用 `t.Run` 分别执行；
4. 先确认失败 case 的输出可读，再运行完整 Test。

## 完成后复盘

- 每个 case 名称能否在不看输入值时说明失败原因？
- 哪个 case 保护正常路径，哪个保护边界，哪个保护错误契约？
- 如果实现发生重构，这些测试是否仍只依赖公开行为？
