# 错误要同时服务人和程序

读取配置失败时，错误既要让使用者知道“哪一步、哪个文件出了问题”，也要让上层代码继续判断底层原因。这节练习把错误上下文、错误链和资源所有权放在同一条执行路径里处理。

## 一条可靠的读取路径

| 阶段 | 成功后得到什么 | 失败时应保留什么 |
|---|---|---|
| 打开文件 | 一个由当前函数负责的文件句柄 | 操作名称、文件路径和底层文件错误 |
| 解码 JSON | 一个可用的配置值 | 解码阶段的上下文和原始语法错误 |
| 返回结果 | 已完成读取的配置 | 所有已取得资源都已经释放 |

错误文案负责补充上下文，错误链负责保留类型语义。只把底层错误格式化成普通字符串，会让 `errors.Is` 和 `errors.As` 失去继续判断原因的能力。

## 谁取得资源，谁安排释放

文件成功打开后，当前函数就获得了资源所有权。最稳妥的做法是在这个时刻立即安排关闭，让后续的成功和失败分支共享同一个清理保证。

> `defer` 不是越早写越好。只有确认资源已经成功取得后，才能对它安排关闭。

## 动手顺序

1. 先运行 Test，观察公开测试要求调用方能够识别哪类底层错误；
2. 沿着 `Load` 的每个返回点检查错误是否既有上下文又保留 cause；
3. 确认文件成功打开后的所有路径都会关闭资源；
4. 再次运行 Test，根据第一条有效失败信息迭代。

完成时，你的实现应满足两个独立条件：调用者能看懂错误发生在哪里，也能用标准错误检查继续识别根因。

## 完成后复盘

- 如果解码失败，文件为什么仍然必须关闭？
- 你把资源所有权的边界放在了哪里？
