# 基于共享变量的并发：同步、锁和数据竞争

第 8 章用 goroutine 和 channel 展示了通信式并发，它有意避开了共享变量的许多陷阱。《Go 程序设计语言》第 9 章回到更传统也更危险的并发模型：多个 goroutine 访问同一份状态。后端服务中，这类状态无处不在：缓存、连接池、计数器、限流器、任务队列、内存索引和统计指标。

共享变量并发的核心问题是：多个 goroutine 同时访问同一变量时，谁能读，谁能写，什么时刻能看到哪些写入？如果这些问题没有同步保证，程序可能偶尔错、偶尔崩、偶尔看似正常，最难排查。

## 并发安全不是默认属性

如果一个函数或类型在多个 goroutine 并发调用时仍然正确，我们说它是并发安全的。并发安全是例外，不是默认规则。除非文档明确说明，否则不要假设某个类型可以被多个 goroutine 同时读写。

包级导出函数通常应该是并发安全的，因为调用方无法知道它们内部是否共享状态。相反，大多数普通对象和数据结构，例如 map、slice、bytes.Buffer，并不自动并发安全。

```go
var counts = map[string]int{}

func Add(status string) {
    counts[status]++ // 并发调用时不安全
}
```

要让它安全，必须限制访问或加同步。

## 数据竞争：最危险的竞争条件

数据竞争发生在：两个或更多 goroutine 并发访问同一个变量，且至少一个访问是写，并且它们之间没有同步。

经典例子是银行余额：

```go
var balance int

func Deposit(amount int) {
    balance = balance + amount
}

func Balance() int {
    return balance
}
```

`balance = balance + amount` 看起来是一行，但实际包含读、加、写多个步骤。两个 goroutine 同时执行时，可能丢失其中一次更新。

```go
go Deposit(200)
go Deposit(100)
```

最终余额不一定是 300。更糟的是，对于 slice、interface、string 这类由多个机器字组成的值，数据竞争可能让程序看到“混合状态”，行为更加不可预测。

经验法则很简单：不要接受所谓“良性数据竞争”。只要有数据竞争，就是 bug。

## 避免数据竞争的三种方式

第一种方式：**不写共享变量**。只读数据在初始化完成后不再修改，多个 goroutine 并发读取是安全的。

```go
var icons = map[string]image.Image{
    "spades.png": loadIcon("spades.png"),
}
```

第二种方式：**把变量限制在单个 goroutine 内**。其他 goroutine 通过 channel 发送请求。第 8 章的并发爬虫中，`seen` map 只由 main goroutine 访问，因此不需要锁。

第三种方式：**允许多个 goroutine 访问，但同一时刻最多一个访问**。这就是互斥锁要解决的问题。

选择哪一种取决于状态形态：如果状态天然属于一个事件循环，用 monitor goroutine 很清楚；如果状态是简单结构并且访问频繁，Mutex 往往更直接。

## sync.Mutex：保护的是不变量

`sync.Mutex` 提供互斥锁。`Lock` 获取锁，`Unlock` 释放锁。

```go
var (
    mu      sync.Mutex // guards balance
    balance int
)

func Deposit(amount int) {
    mu.Lock()
    defer mu.Unlock()
    balance += amount
}

func Balance() int {
    mu.Lock()
    defer mu.Unlock()
    return balance
}
```

锁保护的不是某一行代码，而是一组状态的不变量。比如余额不能在一次取款操作中短暂变成非法值并被其他 goroutine 观察到。临界区应该覆盖完整业务动作。

错误示例：把取款拆成多次加锁的 `Deposit` 和 `Balance`，中间可能被其他 goroutine 插入，导致逻辑竞态。正确做法是整个取款过程持有同一把锁，或拆出“要求锁已持有”的内部函数。

```go
func Withdraw(amount int) bool {
    mu.Lock()
    defer mu.Unlock()

    if balance < amount {
        return false
    }
    balance -= amount
    return true
}
```

Go 的 Mutex 不可重入。不要在持锁时调用另一个会尝试获取同一把锁的导出函数，否则会死锁。

## defer Unlock：简单但要注意范围

复杂函数中，`defer mu.Unlock()` 能避免多个 return 路径忘记解锁。

```go
mu.Lock()
defer mu.Unlock()
```

但 defer 也会把锁持有时间延伸到函数结束。如果函数很大，或者临界区之后还有慢 I/O、网络请求、日志格式化、回调调用，就应该缩小临界区，把持锁逻辑拆成小函数或代码块。

锁内不要做可能阻塞很久的事情，尤其不要在锁内调用未知回调或向可能阻塞的 channel 发送数据，除非你非常清楚调用链。

## sync.RWMutex：读多写少时才值得用

`sync.RWMutex` 允许多个读者并发持有读锁，但写锁互斥。

```go
var mu sync.RWMutex
var balance int

func Balance() int {
    mu.RLock()
    defer mu.RUnlock()
    return balance
}
```

只有当读操作很多、写操作较少、且锁竞争明显时，RWMutex 才可能带来收益。它内部更复杂，无竞争情况下不一定比普通 Mutex 更快。

更重要的是：逻辑上“看起来只读”的函数，不一定真的只读。它可能更新缓存、统计访问次数或刷新过期状态。只要会写共享状态，就必须使用写锁。

## 内存同步：不是只有语句交错这么简单

很多人把并发想象成两个 goroutine 的语句交错执行。但现代 CPU 和编译器会为了效率重排指令、使用本地缓存、延迟写回主存。如果没有同步，另一个 goroutine 不一定能按你想象的顺序看到写入。

channel 通信、Mutex Lock/Unlock、WaitGroup 等同步原语不仅控制执行顺序，也建立内存可见性。它们保证某些写入在另一个 goroutine 读取前已经可见。

因此，像下面这种“只读一行”的函数也需要同步：

```go
func Balance() int {
    return balance // 如果另一个 goroutine 会写，仍然不安全
}
```

并发正确性不是靠“这行很简单”保证的，而是靠明确的 happens-before 关系保证的。

## sync.Once：并发安全的一次性初始化

懒初始化在单 goroutine 中很简单：

```go
if icons == nil {
    loadIcons()
}
```

但并发调用时不安全。一个 goroutine 可能看到 `icons` 已经非 nil，但里面的数据尚未完全初始化。正确方式是 `sync.Once`：

```go
var loadIconsOnce sync.Once
var icons map[string]image.Image

func Icon(name string) image.Image {
    loadIconsOnce.Do(loadIcons)
    return icons[name]
}
```

`Once.Do` 保证初始化函数只执行一次，并且它的内存写入对所有后续调用可见。适合昂贵配置、模板、静态索引、只读缓存等一次性初始化场景。

不要在 `Do` 的初始化函数里做可能永久阻塞或依赖自身再次初始化的逻辑，否则所有等待者都会卡住。

## Race detector：用工具发现运行时数据竞争

Go 工具链内置竞争检测器：

```bash
go test -race ./...
go run -race .
go build -race ./cmd/server
```

它会记录运行时对共享变量的读写和同步事件，一旦发现没有同步保护的并发读写，就打印报告，包括读写位置和 goroutine 调用栈。

race detector 只能发现测试运行中实际发生的数据竞争，不能证明程序完全没有数据竞争。因此并发测试要尽量覆盖真实并发路径：多 goroutine、重复运行、超时、取消、错误分支和高并发场景。

在涉及锁、channel、缓存、worker pool、全局状态的改动中，`go test -race` 应该成为常规验证。

## 并发安全缓存：锁和通信都能解决问题

教材中的 memo 缓存展示了一个典型演进：

1. 普通 map 缓存：顺序正确，并发不安全；
2. 给整个 Get 加 Mutex：安全，但把慢 I/O 串行化；
3. 缩小锁范围：并发提升，但可能重复计算；
4. 每个 entry 带 ready channel：避免重复计算，并通过关闭 channel 广播结果已就绪；
5. 用 monitor goroutine 管理 map：通过 channel 串行处理请求。

这个例子说明：并发设计不只是“加锁”。你需要明确保护什么、等待什么、广播什么、是否允许重复工作、是否要取消。

一个常见模式是用锁保护 map，用每个 entry 的 channel 表示某个 key 的计算完成：

```go
type entry struct {
    res   result
    ready chan struct{}
}
```

第一个请求负责计算并 `close(ready)`；后续请求等待 `<-ready`。关闭 channel 建立了同步关系，因此其他 goroutine 读取结果不会产生数据竞争。

## atomic：适合简单数值，不适合复杂不变量

虽然教材重点放在 Mutex 和 channel，但现代 Go 也常用 `sync/atomic` 的类型化 API，例如 `atomic.Int64`、`atomic.Bool`。它适合计数器、开关、指标这类简单状态。

```go
var requests atomic.Int64
requests.Add(1)
fmt.Println(requests.Load())
```

atomic 不适合维护多个字段之间的不变量。如果一个业务动作需要更新多个变量，或者需要“检查后更新”，Mutex 往往更清楚。

不要为了看起来更快就滥用 atomic。先用 Mutex 写出正确版本，再通过 benchmark 和 profile 判断是否真的需要优化。

## Goroutine 和线程的差异

goroutine 可以粗略类比线程，但更轻量。它们初始栈很小，会按需增长；Go runtime 在少量 OS 线程上调度大量 goroutine。goroutine 在 channel、Mutex、time.Sleep、系统调用等阻塞点让出执行权，调度成本通常低于 OS 线程切换。

`GOMAXPROCS` 控制同时执行 Go 代码的 OS 线程数量，默认通常是 CPU 核心数。I/O 阻塞的 goroutine 不需要一直占用一个线程。

Go 故意不暴露 goroutine ID，避免线程本地存储式的隐式依赖。函数行为应由显式参数、接收者和上下文决定，而不是由“当前在哪个 goroutine”决定。

## 本章工程视角

共享变量并发的核心是纪律。每个共享字段都应该有清晰所有者：只读、单 goroutine 拥有、Mutex 保护、RWMutex 保护、Once 初始化，还是 atomic 管理。没有写清楚的共享状态，迟早会变成线上偶发问题。

评审并发代码时，不要只问“有没有锁”。要问：锁保护的具体不变量是什么？临界区是否覆盖完整业务动作？是否在锁内做慢操作？是否可能死锁？是否复制了含锁结构体？是否用 `go test -race` 跑过真实并发路径？这些问题比语法本身更重要。
