# 基于共享变量的并发：用同步保护状态和不变量

第 8 章刻意强调“通过通信共享数据”。但真实后端里，很多状态天然会被多个 goroutine 访问：缓存、连接池、限流器、指标计数器、内存索引、任务状态表。只要状态被共享，就必须回答一个问题：**谁能读，谁能写，另一个 goroutine 什么时候能看见这些写入？**

这一章围绕一个小场景展开：**多个请求同时更新计数器和缓存时，如何避免数据竞争、丢失更新和偶发崩溃**。你会学习并发安全、data race、`sync.Mutex`、`sync.RWMutex`、`sync.Once`、race detector、`sync/atomic` 以及缓存里的重复计算抑制。

## 你会解决什么问题

我们从一个请求计数器开始。目标是在 100 个 goroutine 同时更新时，最终仍然得到：

```text
total=100
```

这件小事会牵出本章大多数知识：

| 任务 | 需要的同步能力 | 工程关注点 |
|---|---|---|
| 多个 goroutine 更新计数器 | `sync.Mutex` | `total++` 不是原子操作 |
| 保护 map 缓存 | 锁或单 goroutine 所有权 | Go map 并发写会崩溃 |
| 只初始化一次配置 | `sync.Once` | 结果对所有 goroutine 可见 |
| 读多写少状态 | `sync.RWMutex` | 读锁只适合真正只读 |
| 简单指标计数 | `sync/atomic` | 不适合维护多个字段不变量 |
| 验证并发 bug | `go test -race` | 只能发现被测试触发的竞争 |

## 并发安全不是默认属性

如果一个函数或类型被多个 goroutine 同时调用仍然正确，我们说它是并发安全的。并发安全是例外，不是默认规则。除非文档明确说明，否则不要假设某个类型可以被并发读写。

普通 `map`、`slice`、`bytes.Buffer`、大多数业务结构体都不是自动并发安全的：

```go
var counts = map[string]int{}

func Add(status string) {
    counts[status]++ // 并发调用时不安全
}
```

包级导出函数通常应当并发安全，因为调用方很难知道包内部是否共享状态。相反，普通对象是否并发安全要由类型文档、字段注释或方法设计说明。

## Data race：并发读写没有同步就是 bug

数据竞争发生在：两个或更多 goroutine 并发访问同一个变量，至少一个是写操作，并且它们之间没有同步。

经典例子是余额累加：

```go
var balance int

func Deposit(amount int) {
    balance = balance + amount
}
```

`balance = balance + amount` 看起来是一行，实际包含读取、相加、写回。两个 goroutine 同时执行时，可能丢失其中一次更新。

更危险的是由多个机器字组成的值，例如 slice、string、interface。并发写可能让另一个 goroutine 看到“混合状态”：指针来自一次写入，长度来自另一次写入，行为就变得不可预测。

经验法则很简单：不要接受所谓“良性数据竞争”。即使只是日志、指标或缓存，只要并发读写没有同步，就是 bug。

## 逻辑竞态：没有 data race 也可能业务错误

数据竞争是最危险、也最容易被工具发现的一类竞态。但没有 data race 不代表逻辑一定正确。

例如取款流程如果拆成多个各自加锁的步骤：

```go
Deposit(-amount)
if Balance() < 0 {
    Deposit(amount)
    return false
}
```

每个函数内部也许都加了锁，但整个“检查并更新”的业务动作不是原子的。另一个 goroutine 可能在步骤之间插入，导致错误拒绝或状态短暂非法。

锁保护的不是某一行代码，而是一组状态的不变量。临界区应该覆盖完整业务动作。

## 避免数据竞争的三条路

gopl-zh 把避免数据竞争总结为三种方式。

第一种：**不写共享变量**。初始化后不再修改的数据可以被任意 goroutine 并发读取。

```go
var icons = map[string]image.Image{
    "spades.png": loadIcon("spades.png"),
}
```

第二种：**把变量限制在单个 goroutine 内**。其他 goroutine 通过 channel 发请求，这叫 monitor goroutine。第 8 章的爬虫中，`seen` map 只由主 goroutine 访问，因此不需要锁。

第三种：**允许多个 goroutine 访问，但同一时刻最多一个访问**。这就是互斥锁要解决的问题。

选择哪一种取决于状态形态：事件流和所有权转移适合 channel；简单共享结构和频繁读写通常用 Mutex 更直接；只读数据则应尽量在启动并发前准备好。

## sync.Mutex：保护共享状态

`sync.Mutex` 提供互斥锁：

```go
var (
    mu      sync.Mutex // guards balance
    balance int
)

func Deposit(amount int) {
    mu.Lock()
    defer mu.Unlock()
    balance += amount
}
```

惯例是把锁和它保护的变量放在一起，并用注释说明关系：`mu guards balance`。对于结构体字段，也可以写在字段旁边或类型文档中。

`defer mu.Unlock()` 能保证多个 return 路径都释放锁。小函数里这是推荐写法。但它也会让锁一直持有到函数返回；如果函数里还有慢 I/O、日志格式化、回调调用或 channel 发送，就应该缩小临界区。

## Mutex 不可重入：持锁时不要调用会再加锁的函数

Go 的 `sync.Mutex` 不可重入。一个 goroutine 持有锁后，如果再次调用同一把锁的 `Lock`，会把自己卡住。

```go
func Withdraw(amount int) bool {
    mu.Lock()
    defer mu.Unlock()
    Deposit(-amount) // Deposit 也会 Lock：死锁
    return true
}
```

常见解决方式是拆出一个“要求锁已持有”的内部函数：

```go
func Deposit(amount int) {
    mu.Lock()
    defer mu.Unlock()
    deposit(amount)
}

// deposit requires mu to be held.
func deposit(amount int) {
    balance += amount
}
```

这种写法把规则写进函数名、注释和可见性：导出函数负责加锁，未导出 helper 假设调用方已经持锁。

## sync.RWMutex：读多写少时才值得用

`sync.RWMutex` 允许多个读者同时持有读锁，但写锁仍然互斥：

```go
var mu sync.RWMutex
var cache map[string]string

func Get(key string) string {
    mu.RLock()
    defer mu.RUnlock()
    return cache[key]
}
```

它只适合读很多、写较少、锁竞争明显的场景。无竞争时，RWMutex 不一定比 Mutex 更快，而且更容易误用。

最重要的是：逻辑上“看起来只读”的函数，不一定真的只读。它可能更新缓存、刷新过期状态或记录访问次数。只要会写共享状态，就必须使用写锁。

## 内存同步：锁和 channel 也保证可见性

并发不只是语句交错。CPU 和编译器可能重排指令、缓存写入、延迟可见。如果没有同步，另一个 goroutine 不一定按你想象的顺序看到数据。

Mutex 的 Unlock 和后续 Lock、channel 发送和接收、关闭 channel 和接收关闭事件、WaitGroup 的等待，都能建立 happens-before 关系。它们不仅控制执行顺序，也保证某些写入对后续读取可见。

因此下面这种“只读一行”也需要同步：

```go
func Balance() int {
    return balance // 如果另一个 goroutine 会写，仍然不安全
}
```

并发正确性不是靠“这行很简单”保证的，而是靠明确同步保证的。

## sync.Once：并发安全的一次性初始化

懒初始化在单 goroutine 中很简单：

```go
if config == nil {
    config = loadConfig()
}
```

并发调用时却不安全。一个 goroutine 可能看到 `config` 已经非 nil，但内部字段尚未完全初始化。正确方式是 `sync.Once`：

```go
var once sync.Once
var config map[string]string

func Config() map[string]string {
    once.Do(func() {
        config = loadConfig()
    })
    return config
}
```

`Once.Do` 保证函数只执行一次，并且初始化函数里的写入对后续调用可见。适合昂贵配置、模板、只读索引、全局正则、静态元数据等一次性初始化场景。

不要在 `Do` 的函数里执行可能永久阻塞、依赖自身再次初始化或需要可取消请求上下文的操作，否则所有等待者都会一起卡住。

## Race detector：用运行时工具发现数据竞争

Go 工具链内置竞争检测器：

```bash
go test -race ./...
go run -race .
go build -race ./cmd/server
```

它会记录运行时对共享变量的读写和同步事件，一旦发现没有同步保护的并发读写，就打印报告，包括读写位置和 goroutine 调用栈。

race detector 只能发现本次运行实际触发的数据竞争，不能证明程序完全没有并发 bug。因此并发测试要尽量覆盖真实路径：多 goroutine、重复运行、超时、取消、错误分支和高并发输入。

在涉及锁、channel、缓存、worker pool、全局状态的改动中，`go test -race` 应成为常规验证。

## sync/atomic：适合简单数值，不适合复杂不变量

现代 Go 提供类型化 atomic API，例如 `atomic.Int64`、`atomic.Bool`：

```go
var requests atomic.Int64
requests.Add(1)
fmt.Println(requests.Load())
```

atomic 适合计数器、开关、指标这类单一状态。它比锁更轻，但不适合维护多个字段之间的不变量。

如果一个业务动作需要多次 atomic 操作，或需要“检查后更新”，通常应该改用 Mutex、channel 所有权，或重新设计状态模型。不要为了看起来高级而把清楚的锁改成难审查的 atomic 序列。

## 并发缓存：锁和 channel 可以配合

gopl-zh 的 memo 缓存展示了一个很好的演进过程：

1. 普通 map：顺序正确，并发不安全；
2. 给整个 Get 加 Mutex：安全，但慢 I/O 被串行化；
3. 缩小锁范围：并发提升，但同一个 key 可能重复计算；
4. 每个 entry 带 `ready` channel：第一个请求负责计算，后续请求等待结果广播；
5. 用 monitor goroutine 管理 map：通过 channel 串行处理请求。

其中 entry + ready 的核心结构是：

```go
type entry struct {
    res   result
    ready chan struct{} // closed when res is ready
}
```

第一个 goroutine 创建 entry、计算结果、写入 `res`，然后 `close(ready)`。其他 goroutine 等待 `<-ready` 后再读取结果。关闭 channel 建立同步关系，因此它们能安全看到第一个 goroutine 写入的结果。

这个例子说明：并发设计不只是“加锁”。你要明确保护什么、等待什么、是否允许重复工作、谁广播结果、谁取消请求。

## 共享变量并发概念回看

| 概念 | 最小定义 | 工程判断 |
|---|---|---|
| 并发安全 | 并发调用仍然正确 | 文档是否明确说明可并发使用 |
| data race | 并发读写同一变量且无同步 | 是否能用 race detector 触发 |
| 逻辑竞态 | 同步存在但业务动作非原子 | 锁是否覆盖完整不变量 |
| 不变数据 | 初始化后不再写 | 是否可在启动并发前准备好 |
| monitor goroutine | 单 goroutine 拥有状态 | 请求协议是否清楚 |
| Mutex | 同时只允许一个 goroutine 访问 | 锁保护哪些字段 |
| RWMutex | 多读单写锁 | 读路径是否真正不写 |
| Once | 只执行一次初始化 | 初始化是否不会永久阻塞 |
| happens-before | 同步建立可见性顺序 | 读写之间是否有同步关系 |
| atomic | 原子读写简单状态 | 是否维护多个字段不变量 |
| race detector | 运行时竞争检测 | 测试是否覆盖真实并发路径 |

## 本章工程视角

共享变量并发的核心是纪律。每个共享字段都应该有清晰所有者：只读、单 goroutine 拥有、Mutex 保护、RWMutex 保护、Once 初始化，还是 atomic 管理。没有写清楚的共享状态，迟早会变成线上偶发问题。

评审并发代码时可以用这组问题自查：

- 哪些变量会被多个 goroutine 访问？其中有没有写操作？
- 每个共享字段由哪把锁、哪个 goroutine 或哪个 Once 管理？
- 锁保护的是哪些不变量，而不只是哪些代码行？
- 是否在持锁时做慢 I/O、发送 channel 或调用未知回调？
- 是否复制了包含 Mutex 的结构体？
- 读路径是否真的只读，还是偷偷更新缓存和指标？
- 是否用 `go test -race` 跑过真实并发路径？

能回答这些问题，你就不只是“会用锁”，而是能设计可解释、可验证、可维护的并发状态边界。
