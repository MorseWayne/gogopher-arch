# 函数：用签名、错误和资源边界组织业务步骤

函数不是把几行代码包起来这么简单。真实后端里，一个请求通常会经历 **解析输入 → 校验规则 → 执行业务 → 释放资源 → 返回结果或错误**。函数签名就是这些边界的第一份说明书：调用方要提供什么，成功时拿到什么，失败时如何继续排查。

这一章会围绕一个小场景展开：你要实现一个任务导入流程，把字符串里的耗时解析出来，补充错误上下文，必要时把处理逻辑拆成可测试的小函数，并确保资源释放不会因为多个 return 分支而遗漏。

## 你会解决什么问题

我们从一个看似简单的输入开始：

```go
input := "45m"
```

目标输出是：

```text
duration=45min
```

这件小事会牵出本章大多数知识：

| 任务 | 需要的函数能力 | 工程关注点 |
|---|---|---|
| 把字符串解析成分钟数 | 函数签名、多返回值 | 成功和失败都要表达清楚 |
| 处理非法输入 | `error` 返回和包装 | 错误信息要能定位哪个输入失败 |
| 复用校验逻辑 | 小函数和函数值 | 业务步骤可以单独测试 |
| 处理资源 | `defer` | 获取成功后尽快安排释放 |
| 避免隐藏状态 | 闭包 | 捕获变量要可见、可控 |

## 函数声明：签名先表达边界

函数声明由函数名、参数列表、返回值列表和函数体组成：

```go
func name(parameterList) (resultList) {
    // body
}
```

一个最小例子：

```go
func minutesText(minutes int) string {
    return fmt.Sprintf("duration=%dmin", minutes)
}
```

签名里真正重要的是类型序列。参数名和返回值名帮助阅读，但不参与函数类型判断：

```go
func add(x, y int) int { return x + y }
func sub(a, b int) int { return a - b }
```

这两个函数的类型都是 `func(int, int) int`。

Go 没有默认参数，也不能按参数名传参。因此签名要短而明确。参数太多时，通常说明函数承担了太多职责，或者需要把一组配置建模成结构体。

## 参数传递：Go 是值传递

函数调用会把实参的值赋给形参。普通值被复制，函数里修改形参不会改变调用方变量：

```go
func reset(x int) {
    x = 0
}

n := 10
reset(n)
fmt.Println(n) // 10
```

但指针、slice、map、channel、函数等值内部可能引用共享数据。把 map 传给函数仍然是值传递，只是复制的 map header 指向同一张底层哈希表：

```go
func markDone(tasks map[string]bool, id string) {
    tasks[id] = true
}
```

这不是“Go 有时按引用传参”，而是值里包含引用。写函数时要明确：它会不会修改传入的数据？如果会，函数名、类型或文档应该让调用方看得出来。

## 多返回值和 error：失败是显式结果

Go 常用多返回值表达“结果 + 错误”：

```go
func parseMinutes(input string) (int, error) {
    text, ok := strings.CutSuffix(input, "m")
    if !ok {
        return 0, fmt.Errorf("duration %q must end with m", input)
    }

    minutes, err := strconv.Atoi(text)
    if err != nil {
        return 0, fmt.Errorf("parse duration %q: %w", input, err)
    }
    return minutes, nil
}
```

`error` 是普通值，不是异常。对于可预期失败，例如输入非法、文件不存在、网络超时、权限不足，应该返回 error，让调用方决定下一步。

调用方通常先处理错误，让成功路径保持左对齐：

```go
minutes, err := parseMinutes(input)
if err != nil {
    return err
}

fmt.Println(minutes)
```

不要把主要逻辑包在深层 `else` 里。错误优先不是为了多写几行，而是为了让失败路径和成功路径都容易扫描。

## 错误处理：传播、包装、降级和终止

拿到 error 后，调用方必须做选择。常见策略如下：

| 策略 | 适用场景 | 注意点 |
|---|---|---|
| 向上传播 | 当前层无法处理 | 不要丢掉原始错误 |
| 添加上下文后传播 | 需要说明任务 ID、文件名、输入参数 | 用 `%w` 保留错误链 |
| 重试 | 临时网络失败、限流 | 要限制次数或时间 |
| 记录后继续 | 非关键功能降级 | 日志要能关联请求或任务 |
| 终止程序 | `main` 无法继续启动 | 库函数不要随意 `log.Fatal` |
| 明确忽略 | 失败确实无影响 | 用变量名或代码结构表达意图 |

```go
func loadConfig(path string) ([]byte, error) {
    data, err := os.ReadFile(path)
    if err != nil {
        return nil, fmt.Errorf("read config %s: %w", path, err)
    }
    return data, nil
}
```

这里的 `read config app.yaml: permission denied` 比单独的 `permission denied` 更容易排查，因为它带上了业务上下文。

## 递归：适合树和图，但退出条件必须清楚

递归函数会调用自身，适合处理树形结构。gopl-zh 第 5 章用 HTML 节点树和网页链接抓取器展示递归：访问当前节点，再访问子节点或后续链接。

一个最小树遍历模型：

```go
type Node struct {
    Value    string
    Children []*Node
}

func visit(n *Node) {
    if n == nil {
        return
    }
    fmt.Println(n.Value)
    for _, child := range n.Children {
        visit(child)
    }
}
```

递归的三个问题要同时回答：

1. 基线条件是什么？例如 `n == nil` 时停止。
2. 每次递归是否靠近基线？例如访问更小的子树。
3. 是否可能重复访问？图、网页链接、依赖关系通常需要 visited 集合。

## 函数值：把行为作为参数

函数在 Go 中是一等值，可以赋给变量、作为参数传递、从函数返回。

```go
func square(n int) int { return n * n }

f := square
fmt.Println(f(3)) // 9
```

函数值适合把“流程”和“策略”分离。例如任务过滤器：

```go
func filter(tasks []string, keep func(string) bool) []string {
    var kept []string
    for _, task := range tasks {
        if keep(task) {
            kept = append(kept, task)
        }
    }
    return kept
}
```

调用方传入不同策略：

```go
urgent := filter(tasks, func(task string) bool {
    return strings.Contains(task, "urgent")
})
```

这种模式在排序比较函数、HTTP 中间件、重试策略、测试替身和批处理过滤中都很常见。

## 匿名函数和闭包：小状态要小心藏在哪里

函数字面量可以在表达式里定义匿名函数。匿名函数能访问外层词法环境，这就是闭包：

```go
func counter() func() int {
    var n int
    return func() int {
        n++
        return n
    }
}
```

每次调用 `counter` 都会创建新的 `n`。返回的函数继续持有这个变量，即使 `counter` 已经返回。这说明变量生命周期不只由代码块决定，也由它是否仍可达决定。

闭包适合封装很小的状态，但不要让读者猜它捕获了什么。

<DeepDive title="循环变量捕获为什么仍值得警惕">

新版本 Go 已经改善了常见 range 变量捕获问题，但老代码、手写复用变量、索引变量和闭包里的共享指针仍可能产生误解。课程建议保持一个稳定习惯：如果回调或 goroutine 需要当前值，就把它作为参数传进去，让意图写在函数签名里。

## defer：让清理靠近资源获取

`defer` 会把函数调用推迟到当前函数返回前执行。多个 defer 按后进先出顺序执行。

```go
f, err := os.Open(name)
if err != nil {
    return err
}
defer f.Close()

return process(f)
```

它适合成对操作：打开/关闭、加锁/解锁、连接/断开、记录进入/退出。关键原则是：**资源获取成功后，尽快写 defer**。

<ExamplePair
  title="资源释放：多个 return 分支 vs defer"
  leftTitle="容易漏掉分支"
  rightTitle="释放靠近获取"
  left={`f, err := os.Open(name)

    return err

    f.Close()
    return errInvalid

  right={`f, err := os.Open(name)
if err != nil {
    return err
}

    return errInvalid
}
return nil`}
/>

循环里大量 defer 要小心，因为 defer 在当前函数返回时才执行，不是在本轮循环结束时执行。处理很多文件、连接或锁时，可以把单次处理拆成小函数：

```go
func processAll(names []string) error {
    for _, name := range names {
        if err := processOne(name); err != nil {
            return err
        }
    }
    return nil
}

func processOne(name string) error {
    f, err := os.Open(name)
    if err != nil {
        return err
    }
    defer f.Close()
    return process(f)
}
```

## panic 和 recover：内部不一致，不是普通失败

`panic` 会中断当前 goroutine 的正常执行，运行已注册的 defer，然后沿调用栈展开。数组越界、nil 指针解引用等运行时错误会 panic，代码也可以主动调用 `panic`。

但健壮业务代码不应该用 panic 处理普通输入错误、I/O 失败或配置缺失。这些都是可预期失败，应该返回 error。

适合 panic 的场景更少，例如：

```go
var routePattern = regexp.MustCompile(`^/users/\d+$`)
```

`MustCompile` 的约定是：源码里的固定正则不合法就是程序员 bug，启动时 panic 比运行时悄悄失败更好。

`recover` 只能在 deferred 函数中捕获当前 goroutine 的 panic。服务端框架可能在请求边界 recover，避免整个进程退出；业务函数内部不应该滥用 recover 把真实 bug 伪装成正常结果。

## 函数概念回看：签名、错误、状态和释放

| 概念 | 最小定义 | 工程判断 |
|---|---|---|
| 函数签名 | 参数类型 + 返回类型 | 调用方能否看懂输入、输出和失败路径 |
| 值传递 | 形参接收实参副本 | 是否会通过指针、slice、map 修改共享数据 |
| 多返回值 | 一次返回多个结果 | `value, error` 是否表达成功和失败 |
| error | 普通接口值 | 是否带上下文，是否保留原始原因 |
| 函数值 | 函数可赋值、传参、返回 | 是否把策略作为参数更清楚 |
| 闭包 | 函数捕获外层变量 | 捕获状态是否隐藏、是否并发安全 |
| defer | 当前函数返回前执行 | 资源获取后是否尽快安排释放 |
| panic | 中断正常控制流 | 是否真的属于程序内部不一致 |

## 本章工程视角

好函数通常有几个共同点：签名短而清楚，失败路径显式，错误信息带上下文，资源释放靠近资源获取，可变状态不藏在难懂的闭包里。它不一定很“抽象”，但应该让调用方知道怎么正确使用它。

写函数时可以用这组问题自查：

- 调用方能从签名看出需要什么、会返回什么吗？
- 失败时是返回 error，还是误用了 panic？
- 错误信息能定位输入、文件、任务或请求吗？
- 函数是否偷偷修改了传入的 slice、map 或指针？
- defer 的作用域是不是你真正想要的作用域？
- 闭包捕获的变量是否比显式参数更难理解？

如果这些答案清楚，函数就不只是语法单元，而是可以测试、排障和长期维护的业务边界。
