# 测试：把预期行为写成可重复的反馈

《Go 程序设计语言》第 11 章讨论测试。测试不是额外的仪式，而是把你对程序行为的预期写成可重复执行的代码。没有测试，重构只能靠信心；有了好测试，重构、修 bug、升级依赖和优化性能才有安全网。

Go 的测试框架很朴素：文件名、函数名和 `go test` 约定驱动一切。它没有复杂断言 DSL，也不强迫你使用某种测试风格。优点是测试代码和普通 Go 代码一样，缺点是你必须自己认真设计输入、输出和失败信息。

## go test 的基本约定

测试文件以 `_test.go` 结尾。它们不会参与普通 `go build`，只在 `go test` 时编译运行。

测试文件里常见三类函数：

```go
func TestName(t *testing.T) { ... }
func BenchmarkName(b *testing.B) { ... }
func ExampleName() { ... }
```

- `Test` 函数验证行为是否正确；
- `Benchmark` 函数测量固定工作负载下的性能；
- `Example` 函数既是可编译文档，也可以校验输出。

运行当前包测试：

```bash
go test
```

运行整个 module：

```bash
go test ./...
```

打印每个测试函数：

```bash
go test -v
```

只运行匹配名称的测试：

```bash
go test -run 'French|Canal'
```

测试命令会生成临时 main 包来调用测试函数，运行结束后报告 PASS 或 FAIL，并清理临时文件。

## 测试函数：失败信息要帮人定位问题

测试函数签名固定：

```go
func TestIsPalindrome(t *testing.T) {
    if !IsPalindrome("kayak") {
        t.Error(`IsPalindrome("kayak") = false`)
    }
}
```

`t.Error` 和 `t.Errorf` 会报告失败，但不会立刻停止当前测试函数。后面的检查仍会继续执行，这样一次运行可能暴露多个失败点。

如果初始化失败，继续运行没有意义，可以用 `t.Fatal` 或 `t.Fatalf` 停止当前测试：

```go
file, err := os.Open(name)
if err != nil {
    t.Fatalf("Open(%q): %v", name, err)
}
```

好的失败信息通常写成：

```text
f(input) = got, want want
```

它应该包含：被调用的函数、关键输入、实际结果、期望结果。不要只写 `failed` 或 `not equal`，那会逼维护者重新读测试代码才能知道发生了什么。

## 表驱动测试：让新增用例变便宜

Go 社区非常常见的模式是表驱动测试：用结构体切片列出输入和期望，再循环执行。

```go
func TestSplit(t *testing.T) {
    tests := []struct {
        name string
        s    string
        sep  string
        want []string
    }{
        {"basic", "a:b:c", ":", []string{"a", "b", "c"}},
        {"empty", "", ":", []string{""}},
    }

    for _, tt := range tests {
        got := strings.Split(tt.s, tt.sep)
        if !reflect.DeepEqual(got, tt.want) {
            t.Errorf("%s: Split(%q, %q) = %#v, want %#v", tt.name, tt.s, tt.sep, got, tt.want)
        }
    }
}
```

表驱动的价值不是“看起来高级”，而是让新增边界条件变成新增一行数据。修 bug 时尤其有用：先把用户报告变成失败用例，再修改实现，最后确认测试变绿。

现代 Go 还常配合 `t.Run` 做子测试：

```go
for _, tt := range tests {
    tt := tt
    t.Run(tt.name, func(t *testing.T) {
        // ...
    })
}
```

子测试让 `go test -run` 可以定位具体场景，也能让失败输出更清楚。

## 随机测试和 fuzzing：探索你没想到的输入

表驱动测试适合精心挑选的输入。随机测试适合探索更大的输入空间。教材中的回文例子会随机生成回文字符串，再检查 `IsPalindrome` 是否始终返回 true。

随机测试要能复现失败。常见做法是记录 seed：

```go
seed := time.Now().UTC().UnixNano()
t.Logf("seed=%d", seed)
rng := rand.New(rand.NewSource(seed))
```

Go 现在内置 fuzzing，特别适合解析器、编码器、URL/JSON/协议处理和安全敏感输入：

```bash
go test -fuzz=Fuzz
```

基础阶段先把表驱动测试写扎实。等函数输入空间很大、手写用例明显不够时，再引入 fuzzing。

## 测试命令：main 包也能被测试

命令行程序也可以测试。关键是把核心逻辑从 `main` 函数中拆出来，让它接收显式参数和 `io.Writer`：

```go
func echo(out io.Writer, newline bool, sep string, args []string) error {
    fmt.Fprint(out, strings.Join(args, sep))
    if newline {
        fmt.Fprintln(out)
    }
    return nil
}
```

测试时用 `bytes.Buffer` 捕获输出：

```go
var buf bytes.Buffer
err := echo(&buf, true, ",", []string{"a", "b"})
if err != nil {
    t.Fatal(err)
}
if got, want := buf.String(), "a,b\n"; got != want {
    t.Errorf("echo output = %q, want %q", got, want)
}
```

不要在可测试函数里直接调用 `os.Exit` 或 `log.Fatal`。这些应该留在 `main` 中；业务函数返回 error，让测试能检查错误。

## 白盒、黑盒和外部测试包

黑盒测试只通过导出 API 观察行为。它更接近真实调用方，也更不容易因为内部重构而破碎。

白盒测试和被测代码在同一个包，可以访问未导出的函数和变量。它适合检查内部不变量、复杂状态机或难以通过公开 API 触发的边界。

外部测试包使用 `_test` 后缀：

```go
package url_test
```

它会被 `go test` 当成独立包编译，只能访问被测包的导出 API。外部测试包适合集成测试和 API 使用示例，也能避免测试代码造成循环导入。

有时外部测试需要访问少量内部实现，可以在包内添加只参与测试构建的 `export_test.go`，把内部符号临时导出给外部测试。这个技巧要谨慎使用，避免把测试和实现绑得太死。

## 测试替身：隔离外部世界

单元测试不应该真的发送邮件、扣款、写生产数据库或请求第三方 API。可以通过接口或函数变量注入替身对象。

更推荐的方式是小接口：

```go
type Mailer interface {
    Send(to string, body string) error
}

func CheckQuota(mailer Mailer, user string, used int64) error {
    if used < quota*90/100 {
        return nil
    }
    return mailer.Send(user, "quota warning")
}
```

测试里提供 fake：

```go
type fakeMailer struct {
    to   string
    body string
}

func (f *fakeMailer) Send(to, body string) error {
    f.to = to
    f.body = body
    return nil
}
```

如果必须临时替换全局变量，要用 `defer` 或 `t.Cleanup` 恢复，避免污染其他测试：

```go
old := notifyUser
notifyUser = fakeNotify
t.Cleanup(func() { notifyUser = old })
```

测试污染是后端项目里很常见的隐性成本：单独跑通过，整包跑失败，通常就是共享状态没清干净。

## 覆盖率：找到薄弱区域，不追求数字崇拜

测试覆盖率表示测试执行到了哪些代码。Go 内置覆盖率工具：

```bash
go test -cover ./...
go test -coverprofile=c.out ./...
go tool cover -html=c.out
```

HTML 报告会标出被覆盖和未覆盖的语句。它能帮你发现明显缺口，例如错误分支从未执行、某个策略分支没有用例。

但覆盖率不能证明没有 bug。100% 语句覆盖也可能没有检查关键结果；低质量测试可以让数字好看却没有保护价值。更好的目标是：关键业务规则、错误路径、边界输入和历史 bug 都有清晰测试。

## 基准测试：用数据判断优化

基准测试函数以 `Benchmark` 开头：

```go
func BenchmarkIsPalindrome(b *testing.B) {
    for i := 0; i < b.N; i++ {
        IsPalindrome("A man, a plan, a canal: Panama")
    }
}
```

运行：

```bash
go test -bench=.
go test -bench=. -benchmem
```

`b.N` 由测试框架调整，用来获得稳定测量。不要把输入规模错误地绑定到 `b.N`；输入规模应该由单独参数控制：

```go
func benchmarkSort(b *testing.B, n int) { ... }
func BenchmarkSort100(b *testing.B) { benchmarkSort(b, 100) }
func BenchmarkSort10000(b *testing.B) { benchmarkSort(b, 10000) }
```

`-benchmem` 会显示每次操作的字节分配和分配次数。很多 Go 性能问题都和不必要分配有关，但仍要用数据确认，不要凭直觉重写代码。

## pprof：优化前先找到真正瓶颈

当你不知道程序慢在哪里时，基准测试还不够，需要剖析。Go 可以在测试时生成 profile：

```bash
go test -run=NONE -bench=. -cpuprofile=cpu.out
go test -run=NONE -bench=. -memprofile=mem.out
go tool pprof ./pkg.test cpu.out
```

常见 profile：

- CPU profile：谁消耗 CPU；
- heap profile：谁分配内存；
- block profile：goroutine 阻塞在哪里；
- mutex profile：锁竞争在哪里。

优化顺序应该是：先 profile，找到热点；再提出改动；再 benchmark 对比；最后保留回归基准。没有测量的优化经常只是把代码写复杂。

## 示例函数：可执行文档

示例函数以 `Example` 开头：

```go
func ExampleIsPalindrome() {
    fmt.Println(IsPalindrome("A man, a plan, a canal: Panama"))
    fmt.Println(IsPalindrome("palindrome"))
    // Output:
    // true
    // false
}
```

如果包含 `// Output:` 注释，`go test` 会运行示例并比对标准输出。示例同时出现在文档中，成为真实可编译的用法说明。

公共库尤其适合写 Example：它比长篇说明更直观，也能防止文档示例随着 API 变化而失效。

## 避免脆弱测试

脆弱测试会因为微小实现变化失败，即使外部行为没有变。常见原因：

- 断言完整大字符串，但真正关心的只是一个字段；
- 依赖 map 遍历顺序；
- 依赖当前时间、随机数、真实网络；
- 过度检查私有函数调用顺序；
- 共享全局状态未清理。

避免脆弱测试的原则是：只断言你真正关心、且应该稳定的行为。复杂输出可以先解析成结构，再检查关键字段；涉及时间和随机数时注入 clock 和 rng；涉及外部依赖时使用 fake。

## 本章工程视角

测试是一种设计反馈。难测的代码通常依赖隐藏全局状态、混合 I/O 和业务逻辑、错误处理不明确、函数边界过大。为了写好测试，你会被迫把核心逻辑提取出来，让依赖通过参数或接口进入。这本身就会改善设计。

评审测试时，不要只问“有没有测试”。要问：失败信息能否定位问题？是否覆盖错误路径？是否有历史 bug 回归用例？测试是否依赖真实外部服务？是否会污染其他测试？基准测试是否有对比数据？这些问题决定测试能不能真正保护项目。
