## 你会解决什么问题

假设我们有一批订单状态：

```go
statuses := []string{"paid", "pending", "paid", "failed", "pending", "paid"}
```

最终要得到稳定输出：

```text
failed=1 paid=3 pending=2
```

这件小事会牵出本章大多数知识：

| 任务 | 需要的复合类型 | 工程关注点 |
|---|---|---|
| 保存一批订单状态 | slice | 是否共享底层数组，是否需要复制 |
| 按状态计数 | map | key 是否可比较，零值是否可用 |
| 稳定输出结果 | slice + map | map 遍历顺序不稳定，需要排序 key |
| 返回 API 响应 | struct + JSON | 内部字段不能随意泄漏 |
| 写可重复测试 | 稳定文本/DTO | 输出顺序和字段边界必须明确 |

## 数组：固定长度也是类型的一部分

数组是一个由固定长度、特定元素类型组成的序列，定义形式是 `[N]T`：`N` 是长度，`T` 是元素类型。长度是数组类型的一部分，因此 `[3]int` 和 `[4]int` 是两个不同类型，长度也必须能在编译期确定。

```go
var a [3]int             // 3 个 int，默认都是 0
fmt.Println(a[0])        // 第一个元素
fmt.Println(a[len(a)-1]) // 最后一个元素

for i, v := range a {
    fmt.Printf("%d %d\n", i, v)
}
```

数组常见初始化方式有四种。

| 写法 | 示例 | 说明 |
|---|---|---|
| 零值初始化 | `var a [3]int` | 每个元素都是元素类型零值 |
| 顺序字面量 | `q := [3]int{1, 2, 3}` | 按索引 0、1、2 依次填充 |
| 长度推导 | `q := [...]int{1, 2, 3}` | 编译器根据元素个数推导成 `[3]int` |
| 指定索引 | `r := [...]int{99: -1}` | 未指定的位置仍是零值，这里得到长度 100 的数组 |

```go
var q [3]int = [3]int{1, 2, 3}
var r [3]int = [3]int{1, 2}
fmt.Println(r[2]) // 0

symbols := [...]string{0: "pending", 2: "paid"}
fmt.Println(len(symbols), symbols[1]) // 3 ""
```

数组的内存模型很直接：**N 个元素连续组成一个值**。如果元素类型可以比较，那么数组也可以比较；比较时会逐个比较所有元素。

```go
a := [2]int{1, 2}
b := [...]int{1, 2}
c := [2]int{1, 3}
fmt.Println(a == b, a == c) // true false
```

数组在业务代码里不如 slice 常用，因为长度固定，不适合表达动态集合。但数组仍然适合特定大小的数据，例如 SHA-256 摘要是 `[32]byte`。这里长度本身就是业务语义的一部分：摘要就是 32 字节，不应该被随意增删。

函数参数是值传递。把数组传给函数会复制整个数组；函数里修改的是副本，不会影响调用方。如果要修改调用方数组，需要传指针。

多数后端代码更自然地使用 slice，因为请求列表、查询结果、批量任务和日志字段通常都是动态长度。但理解数组很重要，因为 slice 的底层窗口正是建立在数组之上。

## Slice：动态窗口，不是数组本身

slice 是 Go 中最常用的序列类型，定义形式是 `[]T`。它看起来像“没有长度的数组”，但语义完全不同：slice 本身是一个小的描述符，底层引用某个数组的一段连续区间。

slice 常见创建方式如下。

| 写法 | 示例 | 说明 |
|---|---|---|
| 零值 | `var s []int` | `len=0`、`cap=0`、`s == nil` |
| 字面量 | `s := []int{1, 2, 3}` | 隐式创建底层数组，再让 slice 指向它 |
| 从数组切片 | `s := arr[1:3]` | 新 slice 引用数组的子区间 |
| 从 slice 再切片 | `t := s[:2]` | 新 slice 和旧 slice 可能共享同一底层数组 |
| make | `s := make([]int, 2, 8)` | 创建长度 2、容量 8 的 slice |
| append | `s = append(s, 4)` | 追加元素，可能复用或替换底层数组 |

slice 可以理解成下面这样的三元组：

```go
type sliceHeader struct {
    ptr *T // 指向底层数组中第一个可见元素
    len int
    cap int
}
```

真实运行时结构不是给业务代码直接操作的类型，但这个模型足够帮助你理解大多数行为：复制一个 slice 变量，只是复制 `ptr/len/cap`，不会复制底层数组。

```go
months := [...]string{1: "January", 2: "February", 3: "March", 4: "April", 5: "May", 6: "June"}
q2 := months[4:7]
fmt.Println(q2)
```

切片表达式 `s[i:j]` 创建一个新 slice，包含 `i` 到 `j-1` 的元素。省略 `i` 表示从 0 开始，省略 `j` 表示到 `len(s)` 结束。新 slice 的长度是 `j-i`，容量通常是从 `i` 到底层数组末尾。

```go
arr := [...]int{0, 1, 2, 3, 4, 5}
s := arr[2:4]
fmt.Println(s, len(s), cap(s)) // [2 3] 2 4
```

多个 slice 可以共享同一个底层数组。修改一个 slice 的元素，可能影响另一个 slice 看到的数据。

<DeepDive title="为什么小 slice 可能拖住大数组">

`sub := big[:10]` 只创建了一个指向 `big` 底层数组的窗口。只要 `sub` 还活着，底层数组就可能无法被回收。处理大文件、批量导入、缓存预热时，如果只想保留一小段数据，应该主动复制这一小段。

```go
sub := append([]byte(nil), big[:10]...)
```

这样 `sub` 指向新的底层数组，原来的大数组就不再被这段小数据引用。

## len、cap 和 append

`len(s)` 是当前 slice 可见元素数量，`cap(s)` 是从 slice 起点到底层数组末尾的可增长空间。`append` 会在容量足够时复用底层数组；容量不足时分配新数组并复制旧元素。

```go
var values []int
values = append(values, 1)
values = append(values, 2, 3)
fmt.Println(values)
```

调用 `append` 后必须使用它的返回值：

```go
values = append(values, next)
```

不要假设 `append` 一定会或一定不会重新分配。这个不确定性是很多隐藏 bug 的来源。如果你需要保留独立数据，明确复制：

```go
snapshot := append([]string(nil), items...)
```

或者：

```go
snapshot := make([]string, len(items))
copy(snapshot, items)
```

## nil slice 和空 slice

slice 的零值是 `nil`，长度和容量都是 0。空 slice 也可以是非 nil，例如 `[]int{}`。多数情况下，判断 slice 是否为空应该使用 `len(s) == 0`，而不是 `s == nil`。

```go
var a []int
b := []int{}

fmt.Println(len(a), a == nil) // 0 true
fmt.Println(len(b), b == nil) // 0 false
```

除非 API 文档明确区分 nil 和 empty，否则函数应该尽量同等对待二者。JSON 编码时二者可能表现不同：nil slice 可能编码为 `null`，空 slice 编码为 `[]`。这属于跨系统边界，应该按产品协议决定。

## Map：哈希表、索引和集合

map 是无序 key/value 集合，定义形式是 `map[K]V`：`K` 是 key 类型，`V` 是 value 类型。key 类型必须支持 `==` 比较，因为哈希表需要判断两个 key 是否相同；value 类型没有这个限制。

常见创建和初始化方式如下。

| 写法 | 示例 | 说明 |
|---|---|---|
| make | `ages := make(map[string]int)` | 创建可写入的空 map |
| 字面量 | `ages := map[string]int{"alice": 31}` | 创建并初始化 key/value |
| 空字面量 | `counts := map[string]int{}` | 创建可写入的空 map |
| nil map | `var m map[string]int` | 可读、可 `len`、可 `range`，但不能写入 |

```go
ages := map[string]int{
    "alice":   31,
    "charlie": 34,
}

ages["alice"] = 32
delete(ages, "charlie")
```

map 的内存/语义模型可以理解为：**map 变量持有一个哈希表引用**。把 map 传给函数或赋给另一个变量，不会复制整个哈希表；两个变量会指向同一份底层数据。

```go
func bump(counts map[string]int) {
    counts["paid"]++
}

counts := map[string]int{"paid": 1}
bump(counts)
fmt.Println(counts["paid"]) // 2
```

map 元素不是稳定变量，不能对 map 元素取地址：

```go
// _ = &ages["alice"] // compile error
```

原因是 map 可能随着元素增长而搬迁桶或重排内部存储，之前取到的地址可能失效。

```go
counts := map[string]int{}
counts["paid"]++
counts["pending"]++
fmt.Println(counts["paid"])
```

查找不存在的 key 会返回 value 类型的零值。这让计数器写法很简洁：

```go
counts[status]++
```

但有时需要区分“不存在”和“存在但值为零”，这时使用 comma ok 写法：

```go
age, ok := ages["bob"]
if !ok {
    fmt.Println("bob not found")
}
_ = age
```

map 的零值是 nil。读取、`len`、`range`、`delete` 都可以安全作用于 nil map，但写入 nil map 会 panic。因此写入前要用 `make` 或字面量初始化。

```go
var m map[string]int
// m["x"] = 1 // panic
m = make(map[string]int)
m["x"] = 1
```

## Map 遍历顺序故意不稳定

Go 故意不保证 map 遍历顺序。你不能把 `range map` 的输出顺序作为业务逻辑、测试快照或签名输入。

如果需要稳定输出，先收集 key，再排序：

```go
names := make([]string, 0, len(ages))
for name := range ages {
    names = append(names, name)
}
sort.Strings(names)

for _, name := range names {
    fmt.Printf("%s=%d\n", name, ages[name])
}
```

## 用 map 表达 set 和计数器

Go 没有内置 set 类型，但可以用 map 的 key 唯一性表达集合。

```go
seen := map[string]bool{}
for _, id := range ids {
    if seen[id] {
        continue
    }
    seen[id] = true
    fmt.Println(id)
}
```

也可以用 `map[string]int` 做计数器：

```go
counts := map[string]int{}
for _, status := range statuses {
    counts[status]++
}
```

如果 value 完全不重要，有些代码会用 `map[string]struct{}` 节省一点空间。但对初学和业务代码来说，`map[string]bool` 往往更直观。工程上先保证表达清楚，再在确有必要时优化内存。

## Struct：把字段组织成业务对象

结构体是一组命名字段的聚合类型，定义形式是：

```go
type Employee struct {
    ID        int
    Name      string
    Position  string
    Salary    int
    ManagerID int
}
```

每个字段都有名字和类型。相邻字段类型相同时可以合并写，但教程阶段建议先保持一行一个字段，便于阅读和讲解。

```go
type Point struct {
    X, Y int
}
```

结构体常见初始化方式如下。

| 写法 | 示例 | 说明 |
|---|---|---|
| 零值 | `var e Employee` | 每个字段都是对应类型零值 |
| 字段名字面量 | `Employee{ID: 1, Name: "Gopher"}` | 推荐工程代码使用，字段顺序不重要 |
| 顺序字面量 | `Point{1, 2}` | 适合小结构体或包内稳定类型 |
| 指针字面量 | `p := &Point{X: 1, Y: 2}` | 创建结构体并取得地址 |
| new | `p := new(Point)` | 得到指向零值结构体的指针 |

字段通过点操作符访问。结构体变量的字段也是变量，可以直接赋值；结构体指针也可以直接用点操作符访问字段，Go 会自动解引用。

```go
var e Employee
e.Name = "Gopher"

p := &e
p.Position = "Backend Intern"
```

结构体的内存/语义模型和 slice、map 不同：**结构体值本身包含它的字段**。赋值、传参和返回结构体时，默认会复制整个结构体值；如果字段里包含 slice、map、指针等引用型字段，复制的是这些字段的描述符或引用，而不是递归深拷贝所有底层数据。

```go
type Batch struct {
    Name   string
    Orders []string
}

b1 := Batch{Name: "daily", Orders: []string{"paid"}}
b2 := b1
b2.Name = "retry"
b2.Orders[0] = "failed"

fmt.Println(b1.Name)      // daily
fmt.Println(b1.Orders[0]) // failed
```

这里 `Name` 是字符串字段，赋值后两个结构体各自有自己的字段值；`Orders` 是 slice 字段，复制结构体时复制的是 slice 三元组，所以两个结构体仍共享同一底层数组。

结构体字段顺序是类型定义的一部分。相关字段应该放在一起，导出的字段首字母大写，未导出的字段首字母小写。结构体可以包含指向自身类型的指针，从而表达树、链表等递归结构。

结构体零值是所有字段的零值。好的结构体设计会尽量让零值有意义，但不是所有领域对象都适合零值可用。对于必须填写的字段，应该在构造函数或校验函数里显式检查。

## 结构体字面量和指针

结构体字面量有两种常见写法。按字段顺序写：

```go
type Point struct{ X, Y int }
p := Point{1, 2}
```

以及按字段名写：

```go
p := Point{X: 1, Y: 2}
```

工程代码更推荐字段名形式，尤其是字段较多、类型导出、或字段未来可能调整时。字段名形式可读性更好，也更不容易因为字段顺序变化导致误赋值。

较大的结构体通常通过指针传递；如果函数要修改结构体字段，也必须接收指针，因为函数参数本身是值拷贝。

```go
func AwardAnnualRaise(e *Employee) {
    e.Salary = e.Salary * 105 / 100
}
```

## JSON：结构体就是协议边界

JSON 是后端服务最常见的数据交换格式之一。Go 标准库的 `encoding/json` 可以把结构体、slice、map 和基础类型编码为 JSON，也可以从 JSON 解码回 Go 结构。

```go
type Movie struct {
    Title  string
    Year   int  `json:"released"`
    Color  bool `json:"color,omitempty"`
    Actors []string
}
```

结构体字段 tag 控制 JSON 字段名和编码行为。只有导出字段会被 `encoding/json` 默认处理，因此 JSON DTO 的字段通常需要大写开头，再通过 tag 指定外部协议里的小写或下划线字段名。

```go
data, err := json.MarshalIndent(movie, "", "  ")
if err != nil {
    return err
}
fmt.Println(string(data))
```

解码时，结构体可以只声明自己关心的字段，其他 JSON 字段会被忽略。这很适合接入第三方 API，但也要小心：字段被忽略可能掩盖协议变更。重要接口应该有测试覆盖和必要的 schema 校验。

<DeepDive title="为什么 JSON DTO 不应该和内部模型无脑共用">

内部模型服务于业务规则，响应 DTO 服务于外部协议。它们变化的理由不同：内部模型可能增加缓存字段、权限字段、审计字段；响应 DTO 则要保证对前端和第三方调用方的兼容性。

如果直接把内部模型编码成 JSON，短期确实省代码，长期却容易出现两个问题：

- 内部字段被意外暴露；
- 外部协议被内部重构牵连。

因此，边界层做一次显式转换不是“多余样板”，而是把内部变化和外部协议隔离开。

</DeepDive>

## 请求、响应和内部模型不要随意混用

真实后端项目里，结构体不是越少越好。很多初学者会把数据库模型、请求参数、响应 DTO 和内部领域对象混成一个结构体，短期省事，长期会把边界问题扩散到所有地方。

更稳妥的做法是按边界建模：

```go
type CreateUserRequest struct {
    Name  string `json:"name"`
    Email string `json:"email"`
}

type User struct {
    ID           int64
    Name         string
    Email        string
    PasswordHash string
}

type UserResponse struct {
    ID   int64  `json:"id"`
    Name string `json:"name"`
}
```

这样可以避免把内部字段泄漏给前端，也方便在请求层做校验、在响应层隐藏敏感信息、在内部模型中保持业务语义。

## 概念回看：四类复合类型怎么区分

读完数组、slice、map、struct 和 JSON 边界后，再回头看这张表会更容易理解。它不是开篇要背的定义，而是帮助你把前面的细节收束成判断框架。

| 类型 | 定义形式 | 初始化方式 | 内存/语义模型 | 最常见误区 |
|---|---|---|---|---|
| 数组 | `[N]T` | 零值、顺序字面量、索引字面量、`...` 推导长度 | 固定长度连续元素，长度属于类型，赋值和传参会复制整个数组 | 把数组当成动态列表，或忽略传参复制成本 |
| slice | `[]T` | 字面量、从数组/slice 切片、`make([]T, len, cap)`、`append` | 三元组：指针、长度、容量；引用底层数组窗口 | 以为切片就是复制，或忘记接收 `append` 返回值 |
| map | `map[K]V` | `make(map[K]V)`、map 字面量、空字面量 | 哈希表引用，key 必须可比较，遍历顺序不稳定 | 写入 nil map，依赖遍历顺序，对 map 元素取地址 |
| struct | `type T struct { ... }` | 零值、顺序字面量、字段名字面量、`&T{}` | 字段按定义聚合成一个值，字段顺序参与类型定义；传参默认复制 | 内部模型直接作为 JSON 响应，或滥用顺序字面量 |

后续写 Go 代码时，可以把这张表当作 review checklist：看到集合先判断是否需要稳定顺序，看到切片先判断是否共享底层数组，看到结构体响应先判断是否跨越了 API 边界。

## 本章工程视角

复合类型真正考验的是“共享”和“边界”。slice 共享底层数组，map 是引用类型且顺序不稳定，struct tag 会影响外部协议，JSON 解码可能忽略未知字段。你需要在每个边界上明确：数据是否独立？顺序是否稳定？字段是否可以为空？修改是否会影响调用方？

写小程序时，这些问题看起来不严重；写服务时，它们会变成内存泄漏、偶发测试失败、API 兼容性事故和数据泄漏。理解复合类型，就是理解 Go 后端数据流的基本形状。

## 复盘清单

- 看到 `s[a:b]` 时，能判断它是否复制了底层数据。
- 看到 `append` 时，会检查是否使用了返回值。
- 看到 `range map` 输出时，会问它是否需要稳定顺序。
- 看到结构体 JSON 响应时，会检查它是不是内部模型直出。
- 看到练习或测试输出时，会优先保证文本顺序和字段边界稳定。
