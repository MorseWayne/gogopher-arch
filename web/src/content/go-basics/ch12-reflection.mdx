# 反射：在运行时观察类型和值，但把风险留在边界层

Go 是静态类型语言。大多数时候，变量类型、字段、方法和赋值关系都在编译期确定，编译器会帮你发现错误。反射提供了另一种能力：**在运行时检查类型和值**，根据字段、方法和标签做通用处理，甚至修改变量。

这一章围绕一个小场景展开：**你要写一个小型配置/JSON 标签检查器，能读取任意结构体字段信息，但不能把反射的脆弱性扩散到业务代码里**。你会学习 `reflect.Type`、`reflect.Value`、`Kind`、可寻址/可设置、结构体标签、方法集，以及什么时候用接口、泛型或代码生成替代反射。

## 你会解决什么问题

我们从一个最小任务开始：读取结构体字段上的 JSON 标签。

```go
type User struct {
    Name string `json:"name"`
}
```

目标输出是：

```text
json=name
```

这件小事会牵出本章大多数知识：

| 任务 | 需要的反射能力 | 工程关注点 |
|---|---|---|
| 读取字段标签 | `reflect.Type`、`StructField.Tag` | tag 会影响外部协议 |
| 观察任意值 | `reflect.Value`、`Kind` | 调用方法前要检查 Kind |
| 修改传入变量 | `Elem`、`CanSet`、`Set` | 必须传入可设置目标 |
| 编写通用编码器 | 递归遍历 slice/map/struct | nil、环和未导出字段要处理 |
| 枚举方法 | `NumMethod`、`Method` | 业务代码不要依赖字符串方法名 |
| 控制风险 | 接口、泛型、代码生成 | 反射应封装在小边界里 |

## 为什么需要反射

如果你只处理明确类型，普通函数和接口就够了：

```go
func FormatUser(user User) string {
    return user.Name
}
```

但 `fmt.Sprint`、`encoding/json`、ORM、验证器、配置绑定器和测试比较工具面对的是“任意类型”。这些类型可能在库作者写代码时还不存在，库只能在运行时观察它们。

最朴素的方式是 type switch：

```go
func Sprint(x any) string {
    switch x := x.(type) {
    case string:
        return x
    case int:
        return strconv.Itoa(x)
    case bool:
        return strconv.FormatBool(x)
    default:
        return "???"
    }
}
```

问题是类型组合无限多：`[]float64`、`map[string][]string`、结构体、指针、接口嵌套、自定义命名类型都不可能逐个写分支。

反射解决的是这类问题：函数需要处理一大类没有共同接口的值，并且需要在运行时查看它们的结构。

<PitfallCard
  title="把反射当作普通业务抽象"

  fix="反射只放在框架或基础设施边界；业务层优先使用普通类型、接口、泛型或显式转换。"

## Type 和 Value：类型信息和值信息要分开看

`reflect` 包的两个核心类型是 `reflect.Type` 和 `reflect.Value`。

```go
t := reflect.TypeOf(3)
fmt.Println(t.String()) // int

v := reflect.ValueOf(3)
fmt.Println(v.Type()) // int
fmt.Println(v.Int())  // 3
```

`Type` 描述类型，`Value` 描述具体值。二者都来自接口值里的动态类型和动态值：

```go
var w io.Writer = os.Stdout
fmt.Println(reflect.TypeOf(w)) // *os.File
```

注意这里打印的是动态具体类型 `*os.File`，不是变量的静态接口类型 `io.Writer`。

`Value` 可以转回普通接口：

```go
v := reflect.ValueOf(3)
x := v.Interface()
i := x.(int)
fmt.Println(i)
```

这条路径很绕，但许多通用库会先用反射分析结构，再在边界处把值交回普通 Go 代码。

## Kind：有限的底层类别

Go 的具体类型无限多，但 `Kind` 是有限集合：`Bool`、`Int`、`String`、`Struct`、`Slice`、`Map`、`Ptr`、`Interface`、`Func` 等。

```go
func formatAtom(v reflect.Value) string {
    switch v.Kind() {
    case reflect.Invalid:
        return "invalid"
    case reflect.Bool:
        return strconv.FormatBool(v.Bool())
    case reflect.Int, reflect.Int8, reflect.Int16, reflect.Int32, reflect.Int64:
        return strconv.FormatInt(v.Int(), 10)
    case reflect.String:
        return strconv.Quote(v.String())
    default:
        return v.Type().String()
    }
}
```

`Type` 回答“具体是什么类型”，例如 `time.Duration`；`Kind` 回答“底层属于哪类”，例如 `Int64`。这就是反射能统一处理具名类型和基础类型的原因。

但不是所有 `Value` 方法都能对任意 Kind 调用。对非 slice 调用 `Index`、对非 struct 调用 `Field`、对非 int 调用 `Int` 都会 panic。反射代码必须先检查 Kind。

## 递归遍历：Display 为什么容易变复杂

gopl-zh 的 `Display` 函数是一个调试工具：给定任意值，递归打印它的结构和路径。处理思路大致如下：

```go
func display(path string, v reflect.Value) {
    switch v.Kind() {
    case reflect.Slice, reflect.Array:
        for i := 0; i < v.Len(); i++ {
            display(fmt.Sprintf("%s[%d]", path, i), v.Index(i))
        }
    case reflect.Struct:
        for i := 0; i < v.NumField(); i++ {
            name := v.Type().Field(i).Name
            display(path+"."+name, v.Field(i))
        }
    case reflect.Map:
        for _, key := range v.MapKeys() {
            display(fmt.Sprintf("%s[%v]", path, key), v.MapIndex(key))
        }
    case reflect.Ptr, reflect.Interface:
        if v.IsNil() {
            fmt.Printf("%s = nil\n", path)
            return
        }
        display("*"+path, v.Elem())
    default:
        fmt.Printf("%s = %v\n", path, v)
    }
}
```

这个例子揭示了反射的力量：它能遍历你没有静态类型信息的对象图。也揭示了反射的危险：nil、未导出字段、不可比较 map key、环形结构、不可寻址值都需要特殊处理。

<DeepDive title="为什么环形结构会让通用遍历变难">

链表、图、父子节点互相引用时，递归反射可能无限展开。通用库通常要记录已经访问过的地址和类型，或限制深度。普通业务函数如果类型已知，直接写强类型遍历更清楚，也更容易定义“遇到环时应该怎样”。

</DeepDive>

## 结构体标签：协议映射的元数据

结构体标签是反射最常见的工程应用之一：

```go
type User struct {
    ID    int64  `json:"id" db:"id"`
    Name  string `json:"name" db:"name"`
    Email string `json:"email,omitempty"`
}
```

读取标签：

```go
field, ok := reflect.TypeOf(User{}).FieldByName("Email")
if ok {
    fmt.Println(field.Tag.Get("json"))
}
```

JSON、ORM、参数绑定器、验证器都会用类似方式解析标签。标签不是注释，它会影响外部协议和运行时行为。修改 tag 等同于修改 API、数据库映射或请求绑定规则，应该有测试保护。

## 可寻址和可设置：修改值前先确认

反射读取值相对简单，修改值要满足更多条件。

```go
x := 2
v := reflect.ValueOf(&x).Elem()
v.SetInt(3)
fmt.Println(x) // 3
```

`reflect.ValueOf(x)` 得到的是 x 的副本，不可设置；`reflect.ValueOf(&x).Elem()` 才表示原变量。

常用检查：

```go
v.CanAddr()
v.CanSet()
```

`CanAddr` 表示是否可取地址，`CanSet` 表示是否可以被修改。未导出字段即使可寻址，也通常不能通过反射设置。

```go
reflect.ValueOf(2).SetInt(3) // panic
```

库代码不应该让这种 panic 泄漏给调用方。更好的做法是检查输入是否是非 nil 指针、目标是否可设置、类型是否匹配，然后返回清晰 error。

## JSON 解码为什么要传指针

`encoding/json` 解码需要修改目标变量：

```go
var user User
err := json.Unmarshal(data, &user)
```

如果传 `user` 而不是 `&user`，反射拿到的是副本，不能设置原变量。解码器必须：

- 确认目标是非 nil 指针；
- 通过 `Elem()` 找到可设置值；
- 根据字段标签匹配输入；
- 根据字段类型转换或递归填充；
- 对非法输入返回可诊断 error。

这也是为什么框架边界比反射语法更重要。你需要定义：未知字段怎么办？空字符串如何处理？非法 bool/int 怎么报错？slice 多值如何处理？缺失字段使用零值还是报错？

## 方法集：运行时查看能力，但不要滥用字符串调用

`reflect.Type` 和 `reflect.Value` 可以枚举方法：

```go
func PrintMethods(x any) {
    v := reflect.ValueOf(x)
    t := v.Type()
    for i := 0; i < v.NumMethod(); i++ {
        method := t.Method(i)
        fmt.Println(method.Name, method.Type)
    }
}
```

这可以用于调试、文档工具、RPC 注册或框架适配。但业务逻辑如果依赖“字符串方法名”调用方法，往往会变得脆弱。字段或方法重命名后，编译器无法帮你发现反射字符串里的错误。

如果你只是想表达“这个类型有某个行为”，接口通常更清楚：

```go
type Validator interface {
    Validate() error
}
```

## 反射的替代方案

写反射前先问：

1. 能不能用接口表达行为？
2. 能不能用泛型表达容器或算法？
3. 能不能把类型列表显式写出来？
4. 能不能用代码生成？
5. 反射是否只在启动期、配置加载或低频路径运行？

常见替代：

| 需求 | 优先选择 | 反射是否必要 |
|---|---|---|
| 调用某种能力 | 接口 | 通常不需要 |
| 通用 slice/map 算法 | 泛型 | 通常不需要 |
| 稳定 DTO 转换 | 手写转换 | 不需要 |
| 高性能序列化 | 代码生成 | 可能用于生成器内部 |
| 未知结构体标签绑定 | 反射 | 常见选择 |
| 调试任意对象图 | 反射 | 常见选择 |

反射不是错，但它应该是有理由的选择，而不是因为“看起来通用”。

## 反射概念回看

| 概念 | 最小定义 | 工程判断 |
|---|---|---|
| `reflect.Type` | 运行时类型信息 | 是否需要字段、方法、tag 元数据 |
| `reflect.Value` | 运行时值信息 | 是否要读取或修改具体值 |
| `Kind` | 有限底层类别 | 调用 Value 方法前是否检查 |
| `Interface()` | 从 Value 回到普通接口 | 是否需要类型断言 |
| `Elem()` | 解开指针或接口 | 是否先检查 nil 和 Kind |
| `CanSet()` | Value 是否可修改 | 解码/绑定前是否验证目标 |
| 结构体标签 | 字段上的字符串元数据 | 是否属于外部协议契约 |
| 方法枚举 | 运行时查看导出方法 | 是否能用接口替代 |
| 反射 panic | 调用前置条件不满足 | 库是否转成清晰 error |
| 替代方案 | 接口、泛型、代码生成 | 是否能保留编译期检查 |

## 本章工程视角

反射适合基础设施层，不适合日常业务层。把反射封装在小包里，给外部提供普通函数、结构体和 error。这样业务代码仍然能享受静态类型检查，反射风险也集中可测。

评审反射代码时可以用这组问题自查：

- 是否真的需要处理未知类型，还是接口/泛型就够了？
- 每个 `Value` 操作前是否检查 Kind、nil、CanSet？
- 是否处理未导出字段、缺失字段和非法 tag？
- 是否把 panic 转成调用方能理解的 error？
- 是否避免把 `reflect.Value` 暴露给业务层？
- 字符串字段名和 tag 是否有测试保护？
- 热路径上的反射是否有 benchmark 或 profile 数据？

能回答这些问题，反射就是框架边界的有力工具；回答不清，它就会变成重构、排障和性能优化时最难处理的债务。
