# 方法：把行为放到合适的数据旁边

方法是带接收者的函数。它让某个命名类型拥有自己的行为，也让调用代码更接近领域语言：账户可以增加积分，购物车可以计算总价，缓存可以读取和写入，服务可以处理请求。

这一章会围绕一个小场景展开：**积分账户需要累加积分、保护内部状态，并把相关行为放到数据旁边**。你会看到方法不是“把函数换个写法”，而是在回答三个设计问题：这个行为属于哪个类型？接收者会不会被修改？这个类型应该暴露字段还是通过方法维护不变量？

## 你会解决什么问题

假设我们有一个积分账户：

```go
type Account struct {
    Points int
}
```

业务动作是增加积分：

```text
points=25
```

这件事会牵出本章大多数知识：

| 任务 | 需要的方法能力 | 工程关注点 |
|---|---|---|
| 给账户增加积分 | 指针接收者 | 修改的是原对象还是副本 |
| 读取账户状态 | 值接收者或指针接收者 | 是否需要复制，是否保持一致 |
| 把行为放到数据旁边 | 方法声明 | 是否比普通函数更像领域语言 |
| 组合已有能力 | 结构体嵌入 | 组合不是继承，能力边界要清楚 |
| 保护状态 | 封装 | 字段是否应该直接导出 |

## 方法声明：接收者把函数绑定到类型

方法声明和函数声明很像，只是在函数名前多了一个接收者参数：

```go
type Point struct{ X, Y float64 }

func (p Point) Distance(q Point) float64 {
    return math.Hypot(q.X-p.X, q.Y-p.Y)
}
```

调用时写成：

```go
p := Point{1, 2}
q := Point{4, 6}
fmt.Println(p.Distance(q))
```

`p` 是接收者。Go 没有固定的 `this` 或 `self`，接收者名字通常短而有辨识度，例如 `p Point`、`a *Account`、`s *Server`。同一类型的方法接收者命名应保持一致。

方法不只能定义在 struct 上。只要是同一个包里定义的命名类型，底层类型可以是 slice、map、数字或字符串，也可以定义方法：

```go
type Path []Point

func (path Path) Distance() float64 {
    sum := 0.0
    for i := range path {
        if i > 0 {
            sum += path[i-1].Distance(path[i])
        }
    }
    return sum
}
```

这说明方法服务的是“命名类型的行为”，不是传统类系统里的“类成员”。

## 什么时候用方法，什么时候用普通函数

如果行为天然属于某个领域对象，用方法通常更清楚：

```go
account.Add(15)
cart.Total()
cache.Get(key)
```

如果函数只是无状态转换，普通函数可能更直接：

```go
func NormalizeName(name string) string
func ParseDuration(input string) (time.Duration, error)
```

## 值接收者：复制接收者，适合值语义

方法调用仍然遵循值传递。值接收者会复制接收者：

```go
type Point struct{ X, Y float64 }

func (p Point) Move(dx, dy float64) Point {
    p.X += dx
    p.Y += dy
    return p
}
```

这适合小型、不可变或语义上像值的类型。调用者能理解：原值不会被修改，新值通过返回值拿到。

```go
p := Point{1, 2}
next := p.Move(3, 4)
fmt.Println(p, next) // {1 2} {4 6}
```

像 `time.Duration`、小型坐标、枚举值这类类型，值接收者很自然。

## 指针接收者：修改原对象，避免复制大型结构

如果方法需要修改接收者，应该使用指针接收者：

```go
type Account struct {
    Points int
}

func (a *Account) Add(points int) {
    a.Points += points
}
```

如果写成值接收者：

```go
func (a Account) Add(points int) {
    a.Points += points
}
```

修改只发生在副本上，调用方看到的 `Points` 不会变化。

指针接收者还适合避免复制大型结构体，或者让同一类型的方法接收者风格保持一致。常见经验是：如果某个类型有一个方法需要指针接收者，通常该类型其他方法也使用指针接收者，减少调用者和接口实现上的困惑。

## 自动取址和解引用：调用语法方便，不代表方法集相同

Go 会在合法场景下为方法调用自动取址或解引用。变量 `p` 是 `Point`，但方法需要 `*Point` 接收者时，可以直接写：

```go
p := Point{1, 2}
p.ScaleBy(2) // 编译器隐式使用 (&p).ScaleBy(2)
```

前提是接收者可寻址。临时值不能自动取址：

```go
// Point{1, 2}.ScaleBy(2) // 编译错误：临时值不能取地址
```

反过来，`*Point` 也可以调用值接收者方法，编译器会自动解引用。

这种语法糖让方法调用更顺手，但不要因此忽略方法集差异。接口满足关系看的是方法集，不是某一次调用能不能自动取址。这会在接口章节非常重要。

<DeepDive title="方法集为什么会影响接口实现">

## nil 接收者：可以合法，但必须有语义

某些方法允许 nil 指针作为接收者，只要 nil 对这个类型有明确含义。例如链表中 nil 可以表示空链表：

```go
type IntList struct {
    Value int
    Tail  *IntList
}

func (list *IntList) Sum() int {
    if list == nil {
        return 0
    }
    return list.Value + list.Tail.Sum()
}
```

这不是默认建议。大多数方法在 nil 接收者上会 panic。如果你的方法允许 nil 接收者，应该在类型或方法文档中说明 nil 表示什么。

map 命名类型也常有类似差异：读取 nil map 可以返回零值，写入 nil map 会 panic。同一个类型的不同方法，对 nil 的容忍程度可能不同。

## 结构体嵌入：组合，不是继承

结构体可以嵌入匿名字段，从而提升字段和方法：

```go
type Audit struct {
    CreatedBy string
}

func (a Audit) Label() string {
    return "created_by=" + a.CreatedBy
}

type Order struct {
    Audit
    ID int64
}
```

调用时可以写：

```go
order := Order{Audit: Audit{CreatedBy: "gopher"}, ID: 7}
fmt.Println(order.Label())
```

`Audit` 的方法被提升到 `Order` 上，但这不是继承。`Order` 不是 `Audit`，它只是包含一个 `Audit`。如果某个函数需要 `Audit` 参数，你仍然应该显式传入 `order.Audit`。

嵌入适合把小能力组合进更大的类型。过度嵌入会让类型表面能力变得模糊，甚至产生同名选择器冲突。

## 方法值和方法表达式

选择器 `p.Distance` 可以生成方法值。它把方法和特定接收者绑定成一个函数值：

```go
distanceFromP := p.Distance
fmt.Println(distanceFromP(q))
```

方法值适合“绑定某个对象后稍后调用”：

```go
time.AfterFunc(10*time.Second, rocket.Launch)
```

方法表达式则把接收者变成普通函数的第一个参数：

```go
distance := Point.Distance
fmt.Println(distance(p, q))
```

它们在回调、调度、表驱动策略中有用，但日常业务代码里普通方法调用更常见。

## 方法让集合类型拥有领域行为

gopl-zh 第 6 章的 `IntSet` 示例用 `[]uint64` 实现整数集合，并定义 `Has`、`Add`、`UnionWith`、`String` 等方法。这个例子很适合理解封装：调用方关心集合行为，不应该关心内部是否用位图、map 还是排序 slice。

```go
type IntSet struct {
    words []uint64
}

func (s *IntSet) Add(x int) {
    word, bit := x/64, uint(x%64)
    for word >= len(s.words) {
        s.words = append(s.words, 0)
    }
    s.words[word] |= 1 << bit
}
```

即使结构体暂时只有一个字段，也可以用 struct 包一层，为未来改变内部表示保留空间。

## 封装：保护不变量和演进空间

Go 的可见性规则很简单：包级名字、字段和方法以大写字母开头就会导出，小写开头就只在包内可见。封装的最小单位是包，而不是类。

```go
type Counter struct {
    n int
}

func (c *Counter) N() int     { return c.n }
func (c *Counter) Increment() { c.n++ }
func (c *Counter) Reset()     { c.n = 0 }
```

外部调用者不能直接设置 `n`，只能通过方法改变状态。这样包作者可以维护不变量，例如计数不能任意设成负数、缓存必须和索引同步、连接状态必须按顺序流转。

Go 不强制所有字段私有。很多简单 DTO 会直接导出字段，方便 JSON 编码或调用方构造。但一旦字段导出，它就成为 API 的一部分，未来很难在不破坏兼容的情况下收回。因此导出字段前要确认：调用方直接读写它是否安全？内部表示是否稳定？是否需要校验？

## 方法概念回看：接收者、方法集、嵌入和封装

| 概念 | 最小定义 | 工程判断 |
|---|---|---|
| 方法 | 带接收者的函数 | 行为是否属于这个类型 |
| 值接收者 | 调用时复制接收者 | 类型是否小、不可变、像值 |
| 指针接收者 | 接收者是 `*T` | 是否要修改原对象或避免复制 |
| 自动取址 | 可寻址变量可调用指针方法 | 只是调用语法糖，不等于方法集相同 |
| 方法集 | 类型可用的方法集合 | 会影响接口实现关系 |
| nil 接收者 | 接收者指针为 nil | 是否有明确且文档化的 nil 语义 |
| 嵌入 | 匿名字段提升字段和方法 | 组合能力，不是继承关系 |
| 封装 | 用未导出字段和方法保护状态 | 是否维护不变量和未来演进空间 |

## 本章工程视角

方法应该服务于领域行为，而不是把普通函数机械挪到类型上。`account.AddPoints(15)` 比 `AddPoints(account, 15)` 更能表达业务动作；但 `NormalizeName(name)` 这种无状态转换，用普通函数反而更清楚。

设计方法时可以用这组问题自查：

- 这个行为真的属于接收者类型吗？
- 方法是否需要修改接收者？如果需要，是否用了指针接收者？
- 同一类型的方法接收者风格是否一致？
- 嵌入是否让能力更清楚，还是制造伪继承？
- 导出字段是否会破坏不变量或未来演进空间？
- 方法内部是否隐藏读取全局配置、时间或外部服务？

如果这些问题答案清楚，方法就能让代码更贴近业务语言，同时保持 Go 的简单组合风格。
