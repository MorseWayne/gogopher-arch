# 从第一行 Go 程序开始：建立可观察反馈回路

学习 Go 的第一步不是背完整语法表，而是建立一个很小但完整的反馈回路：写一个源文件，用 `go run` 编译并运行，观察标准输出，再根据编译错误或运行结果调整代码。

本章用一个很具体的场景进入 Go：你要写一个可以被本地 Go 工具链、命令行和 CI 都稳定检查的小程序。它不只是打印一句 hello，而是在训练你识别程序入口、依赖声明、输出格式、工具链反馈和格式化约定。

## 你会解决什么问题

假设你正在给一个新同学准备第一个入职练习：程序运行后必须输出稳定的欢迎信息，方便平台自动检查。

```text
welcome, Gopher
```

这件小事会牵出第一章的核心模型：

| 任务 | Go 概念 | 工程关注点 |
|---|---|---|
| 让文件成为可运行命令 | `package main`、`func main` | 程序入口必须明确 |
| 使用标准库输出文本 | `import "fmt"`、`fmt.Printf` | 依赖要精确，输出要稳定 |
| 快速观察结果 | `go run`、stdout | 先形成最小反馈回路 |
| 验证编译产物 | `go build` | 构建阶段能提前拦截错误 |
| 保持代码一致 | `gofmt`、`goimports` | 格式是团队约定，不是个人偏好 |

## 最小程序：`package main`、`import` 和 `func main`

一个最小可执行 Go 程序通常长这样：

```go
package main

import "fmt"

func main() {
    fmt.Println("Hello, 世界")
}
```

这段程序很短，但已经包含三条重要约定。

第一，源文件以 `package main` 开始。Go 代码通过包组织，普通包用于复用，`main` 包表示当前目录可以构建成独立可执行程序。

第二，`func main()` 是可执行程序入口。Go 运行时完成初始化后会调用 `main.main`。如果你写的是命令行工具、服务启动器或一次性脚本，最外层流程通常从这里开始。

第三，`fmt.Println` 来自标准库 `fmt` 包。`Println` 会把参数格式化为文本，写到标准输出，并追加换行。标准输出是学习阶段最重要的观察窗口之一。

`Println` 适合直接输出一组值；`Printf` 适合控制格式。课程练习通常更偏向 `Printf`，因为自动检查会关注空格、换行和字段顺序。

## `go run`：学习阶段的最短反馈路径

Go 是编译型语言。`go` 命令会把源代码和依赖包编译、链接成机器可以执行的程序。学习阶段最常用的是：

```bash
go run hello.go
```

`go run` 会编译并立即运行程序，适合小实验、课程练习和最小复现。你关注的是：当前代码能不能跑，输出是不是你以为的那样。

如果代码里有语法错误、缺少 import、保留未使用 import，`go run` 会先在编译阶段失败，而不是带着不完整状态进入运行阶段。

  fix="先区分编译错误、运行时 panic、stdout 不匹配和退出状态；不同信号对应不同排查方向。"

后端开发里，很多问题都可以先缩小到这个反馈回路：抽出一个最小程序，确认输入、分支和输出，再把结论放回服务代码。

## `go build`：验证能不能生成产物

当你希望保留编译产物时，可以使用：

```bash
go build hello.go
```

`go build` 会生成可执行文件。学习阶段它像是“更严格一点的确认”：代码不仅能被临时运行，也能被构建成可交付产物。

`go run` 和 `go build` 的区别可以这样理解：

| 命令 | 关注点 | 常见场景 |
|---|---|---|
| `go run` | 快速运行当前代码 | 课程练习、小实验、最小复现 |
| `go build` | 生成并验证产物 | 发布命令、构建镜像、CI 编译检查 |

真实项目还会把 `go test`、`go vet`、容器构建和部署检查接进反馈链路，但第一步仍然是：能不能编译，能不能运行，输出是否稳定。

## `import` 是依赖声明，不是装饰

`import "fmt"` 告诉编译器当前文件需要使用 `fmt` 包。Go 对 import 很严格：缺少必要 import 会编译失败，保留未使用 import 也会编译失败。

```go
import (
    "fmt"
    "os"
)
```

这种严格性一开始可能显得不够宽容，但它能让文件依赖保持干净。对于长期维护的服务来说，一个文件 import 了什么，应该直接反映它依赖了什么能力。

<DeepDive
  title="为什么未使用 import 会报错"
  body="未使用 import 往往意味着代码已经改过但依赖没有清理，或者你以为某段逻辑在运行，实际已经被删除。Go 把这类问题提前变成编译错误，是为了让依赖边界在小文件里也保持清楚。"

实际项目常用 `goimports` 自动维护 import。它会在格式化时添加缺失的包，也会删除未使用的包。你不需要手动和 import 列表搏斗，但需要理解它反映的是文件真实依赖。

## 标准输出、标准错误和退出状态

第一章最常接触的是 stdout，也就是标准输出。`fmt.Println` 和 `fmt.Printf` 默认写到 stdout。课程平台会读取 stdout，并根据预期文本判断练习是否通过。

真实命令行程序还会使用 stderr 和 exit code：

| 信号 | 适合表达什么 |
|---|---|
| stdout | 正常结果，例如生成内容、统计结果、查询输出 |
| stderr | 错误说明、诊断信息、警告 |
| exit code | 程序整体成功或失败 |

本章不要求你马上写完整 CLI 错误处理，但要先形成习惯：输出不仅给人看，也可能给脚本、CI 和监控系统看。稳定输出是工程协作的一部分。

## Go 原生支持 Unicode 输出

经典示例输出的是：

```text
Hello, 世界
```

这说明 Go 源文件和字符串天然适合保存 UTF-8 文本，`fmt.Println` 也能输出中文。你现在不需要深入理解字符串、byte 和 rune 的差异；这些会在基础数据类型章节展开。

本章只需要形成一个直觉：后端服务经常会遇到中文昵称、emoji、日志和 JSON 文本，第一段程序就可以安全地把多语言文本送到标准输出。

## 格式化是团队约定，不是个人偏好

Go 不要求你在每条语句末尾手写分号。编译器会在特定换行位置自动插入分号，因此换行位置也会影响解析。最典型的规则是：函数声明后的左大括号 `{` 应该放在同一行。

不要靠记忆所有格式细节来写 Go。更好的方式是把 `gofmt` 当成工作流的一部分：

```bash
go fmt ./...
```

统一格式的价值不只是“好看”。它减少代码评审里的无意义争论，也让自动化改写、静态分析和团队协作更稳定。一个成熟 Go 项目通常不会讨论“我喜欢哪种缩进”，而是默认让工具处理格式。

## 概念回看：第一段程序里的运行模型

| 概念 | 定义形式 | 使用方式 | 常见误区 |
|---|---|---|---|
| 包声明 | `package main` | 每个 `.go` 文件第一条非注释声明 | 以为任意包都能直接运行 |
| 导入声明 | `import "fmt"` | 当前文件使用外部包时声明 | 留着未使用 import 不清理 |
| 入口函数 | `func main()` | `main` 包里的程序入口 | 在普通库包里寻找 main |
| 标准输出 | `fmt.Println` / `fmt.Printf` | 输出正常结果 | 输出空格、换行不稳定 |
| 快速运行 | `go run file.go` | 编译后立即运行 | 把编译错误当成运行逻辑错误 |
| 构建验证 | `go build` | 生成可执行产物 | 只在本地 run，从不验证产物 |
| 格式化 | `go fmt ./...` | 统一代码格式 | 把格式当成个人风格 |

## 本章工程视角

在真实服务中，第一段 Go 程序不一定是打印 hello。它可能是读取配置、连接数据库、启动 HTTP server 或执行一次迁移任务。但无论程序规模多大，最外层的观察信号仍然很朴素：能否编译，是否成功启动，stdout/stderr 写了什么，退出状态是否符合预期。

因此本章的练习不是为了证明你会写 `fmt.Println`，而是为了建立一种基础习惯：先让最小程序跑起来，再逐步增加复杂度；每增加一步，都通过稳定输出或明确错误确认自己知道程序发生了什么。

- 当前文件是不是一个可运行的 `main` 包。

- stdout 文本是否包含预期换行、空格和字段顺序。

- 提交前能交给 `gofmt` 统一格式。
