# 从第一行 Go 程序开始

学习 Go 不应该先背语法表，而应该先建立一个很小但完整的反馈回路：写一个源文件，用 `go run` 编译并运行，观察标准输出，再根据编译错误或运行结果调整代码。《Go 程序设计语言》第 1 章也是从这个角度进入 Go：先看能运行的程序，再逐步解释包、导入、函数、变量和工具链。

这个训练营会保留经典教材的脉络，但会把内容组织成更适合浏览器内学习和后端工程实践的形式。你不需要一开始理解所有细节；本章的目标是知道程序从哪里开始、输出从哪里出现、工具链为什么会在编译阶段阻止一些不规范代码。

## Hello, World 仍然值得认真看

最小 Go 命令通常长这样：

```go
package main

import "fmt"

func main() {
    fmt.Println("Hello, 世界")
}
```

这段程序很短，但包含了 Go 程序的几个关键约定。

首先，源文件以 `package main` 开始。Go 代码通过包组织，包类似其他语言里的库或模块。`main` 包比较特殊：它表示当前目录可以构建成一个独立可执行程序，而不是只供别人导入的库。

其次，`func main()` 是程序入口。Go 运行时完成初始化后，会调用 `main.main`。如果你写的是命令行工具、服务启动器或一次性脚本，程序的顶层流程通常从这里开始：读取配置，组装依赖，启动服务，最后通过输出和退出状态告诉外部世界发生了什么。

最后，`fmt.Println` 来自标准库 `fmt` 包。`Println` 会把参数格式化为文本，写到标准输出，并追加换行。这个看似简单的行为，是学习阶段最重要的观察手段之一。

## go run 和 go build 的反馈节奏不同

Go 是编译型语言。`go` 命令会把源代码和依赖包编译、链接成机器可以执行的程序。最适合学习阶段的命令是：

```bash
go run hello.go
```

`go run` 会编译并立即运行程序，适合小实验、课程练习和最小复现。你关注的是“当前代码能不能跑、输出是什么”。

如果你希望保留编译产物，可以使用：

```bash
go build hello.go
```

`go build` 会生成可执行文件，适合发布命令、构建服务镜像或在 CI 中验证编译产物。后端工程里，这两个命令的角色不同：`go run` 偏向快速反馈，`go build` 偏向产物验证。

## import 不是装饰，而是依赖声明

`import "fmt"` 告诉编译器这个文件需要使用 `fmt` 包。Go 对 import 很严格：缺少必要 import 会编译失败，保留未使用 import 也会编译失败。

这种严格要求一开始可能让人觉得“不够宽容”，但它能保持代码依赖干净。对于长期维护的服务来说，一个文件 import 了什么，应该直接反映它依赖了什么能力。无用依赖越少，重构和排查越轻。

当程序需要多个包时，通常写成分组形式：

```go
import (
    "fmt"
    "os"
)
```

`gofmt` 会统一格式，常用编辑器也可以在保存时自动格式化。实际项目还常用 `goimports` 自动添加或删除 import。

## Go 原生支持 Unicode 输出

经典示例输出的是：

```text
Hello, 世界
```

这说明 Go 字符串可以自然保存 UTF-8 文本，`fmt.Println` 也能输出中文。你现在不需要深入理解字符串、byte 和 rune 的差异；这些会在基础数据类型章节展开。本章只需要形成一个直觉：Go 的文本处理从一开始就面向多语言输入，而后端服务也经常要处理中文昵称、emoji、日志和 JSON 文本。

## 格式化是团队约定，不是个人偏好

Go 语言不要求你在每条语句末尾手写分号。编译器会在特定换行位置自动插入分号，因此换行位置也会影响解析。最典型的规则是：函数声明后的左大括号 `{` 应该放在同一行。

不要靠记忆所有格式细节来写 Go。更好的方式是把 `gofmt` 当成工作流的一部分：

```bash
go fmt ./...
```

统一格式的价值不只是“好看”。它减少代码评审里的无意义争论，也让自动化改写、静态分析和团队协作更稳定。一个成熟 Go 项目通常不会讨论“我喜欢哪种缩进”，而是默认让工具处理格式。

## 本章工程视角

在真实服务中，第一段 Go 程序不一定是打印 hello。它可能是读取配置、连接数据库、启动 HTTP server 或执行一次迁移任务。但无论程序规模多大，最外层的观察信号仍然很朴素：能否编译，是否成功启动，stdout/stderr 写了什么，退出状态是否符合预期。

因此本章的练习不是为了证明你会写 `fmt.Println`，而是为了建立一种基础习惯：先让最小程序跑起来，再逐步增加复杂度；每增加一步，都通过稳定输出或明确错误确认自己知道程序发生了什么。
