# 底层编程：理解内存边界，但默认保持安全

Go 的日常编程建立在类型安全、边界检查、垃圾回收和可移植运行时之上。你不能随便把字符串当数字写，不能越界访问数组，不能手动释放对象，也不需要知道 goroutine 正在哪个 OS 线程上。这些限制让 Go 程序更容易预测，也更适合团队维护。

《Go 程序设计语言》第 13 章讨论这些安全边界之外的能力：`unsafe`、内存布局、指针转换、`cgo` 和底层系统交互。它们很强，也很危险。大多数业务代码永远不该直接使用这些工具；真正需要时，也应封装在极小范围并用测试、基准和注释守住边界。

## 为什么 Go 要隐藏底层细节

Go 故意不暴露很多实现细节：

- 结构体真实布局由编译器决定；
- goroutine 可以在不同 OS 线程间调度；
- 栈会按需增长，栈上变量可能被移动；
- 垃圾回收器管理对象生命周期；
- map、string、slice、interface 的内部表示不是稳定 API。

这些抽象换来的是可移植性和安全性。你可以在 Linux、macOS、Windows、amd64、arm64 上编写同一套大部分代码，不必关心每个 CPU 的指令和 ABI。

但少数场景需要突破抽象：

- 和操作系统或硬件接口交互；
- 调用 C 库；
- 实现极低层运行时或序列化优化；
- 检查结构体布局和对齐；
- 在性能关键路径上避免不必要转换。

进入这些场景前，先确认：普通 Go、标准库、泛型、代码生成、算法优化、批量 I/O、缓存和 pprof 是否已经用尽。

## unsafe.Sizeof、Alignof、Offsetof

`unsafe` 包里有几个相对安全的观察函数。

```go
fmt.Println(unsafe.Sizeof(float64(0))) // 8
```

`Sizeof` 返回值在内存中固定部分的字节大小。它不会计算指针指向的数据。例如字符串大小通常是两个机器字：数据指针和长度，不包含字符串内容本身。

常见大小直觉：

| 类型 | 典型大小 |
| --- | --- |
| `bool` | 1 字节 |
| `int32` / `float32` | 4 字节 |
| `int64` / `float64` | 8 字节 |
| `int` / `uintptr` / 指针 | 1 个机器字 |
| `string` | 2 个机器字 |
| `[]T` | 3 个机器字 |
| `map` / `chan` / `func` | 1 个机器字 |
| `interface` | 2 个机器字 |

这些大小是理解成本模型的入口，不是跨版本协议。不要把 Go 内部表示直接当网络协议或磁盘格式。

## 对齐和结构体空洞

CPU 访问对齐地址通常更高效。Go 编译器会在结构体字段之间插入填充字节，让字段满足对齐要求。

```go
type A struct {
    Flag bool
    Count int64
    Code int16
}

type B struct {
    Count int64
    Code int16
    Flag bool
}
```

两个结构体包含同样字段，但大小可能不同。`A` 里 `bool` 后面可能插入大量填充，让后面的 `int64` 对齐；`B` 通常更紧凑。

可以用：

```go
unsafe.Sizeof(x)
unsafe.Alignof(x.Field)
unsafe.Offsetof(x.Field)
```

观察大小、对齐和字段偏移。

工程上不要为了节省几个字节把字段顺序改得难读。只有当对象数量巨大、内存占用真实成为问题，并且 benchmark/profile 证明收益明显时，才值得优化布局。优化后要写注释说明原因。

## unsafe.Pointer：逃离类型系统

普通指针 `*T` 指向具体类型变量。`unsafe.Pointer` 可以保存任意类型变量的地址，类似 C 里的 `void*`。

普通指针可以转成 `unsafe.Pointer`，再转成另一种普通指针：

```go
func Float64bits(f float64) uint64 {
    return *(*uint64)(unsafe.Pointer(&f))
}
```

这能观察浮点数位模式，也能破坏类型系统。编译器不再保证你写入的类型和原对象一致。

`unsafe.Pointer` 还可以和 `uintptr` 转换，用于地址计算：

```go
pb := (*int16)(unsafe.Pointer(
    uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b),
))
*pb = 42
```

这类写法必须极其谨慎。`uintptr` 是整数，不是指针。垃圾回收器不会把 `uintptr` 当作对象引用，也不会在对象移动时更新它。不要把地址长期保存在 `uintptr` 变量里。

错误模式：

```go
tmp := uintptr(unsafe.Pointer(&x)) + unsafe.Offsetof(x.b)
pb := (*int16)(unsafe.Pointer(tmp)) // 可能已经失效
```

即使当前 Go 实现没有通用移动 GC，goroutine 栈增长也可能移动栈上变量。写 unsafe 代码不能依赖“当前实现刚好没出事”。

## DeepEqual 和环检测：unsafe 的一个真实用途

`reflect.DeepEqual` 可以比较任意值，但有一些语义不一定符合业务期望。例如 nil slice 和空 slice 会被认为不同：

```go
reflect.DeepEqual([]string(nil), []string{}) // false
```

教材实现了一个自定义 `Equal`，把 nil slice/map 和空 slice/map 视作相等。为了避免递归比较带环结构时无限循环，它记录已经比较过的一对地址和类型：

```go
type comparison struct {
    x, y unsafe.Pointer
    t    reflect.Type
}
```

这展示了 `unsafe` 的合理用法：在极小内部实现里处理 reflect 无法直接表达的地址身份，同时对外暴露普通 API：

```go
func Equal(x, y interface{}) bool
```

调用方不需要接触 `unsafe.Pointer`。风险被封装在包内部，测试可以集中覆盖。

## cgo：调用 C 代码时要付出边界成本

有时 Go 需要调用已有 C 库：硬件驱动、系统库、压缩库、数据库客户端、科学计算库等。`cgo` 是 Go 调用 C 的官方机制。

典型形式：

```go
/*
#cgo LDFLAGS: -lbz2
#include <bzlib.h>
*/
import "C"
```

`import "C"` 前的注释会被 cgo 解析，用于生成 C 绑定。Go 代码可以通过 `C.xxx` 访问 C 类型、函数和常量。

cgo 的成本包括：

- 构建依赖本机 C 编译器和头文件；
- 交叉编译更复杂；
- Go 指针传给 C 有严格规则；
- C 代码不受 Go 内存安全保护；
- 调用边界有额外开销；
- 运行时部署需要考虑动态库和系统差异。

如果只是调用一个命令行工具，`os/exec` 可能更简单；如果库很小，纯 Go 重写可能更可维护；只有当 C 库复杂、成熟且性能/能力不可替代时，cgo 才值得引入。

## 系统调用和平台差异

底层代码常常和 GOOS、GOARCH 绑定。文件描述符、socket 选项、内存映射、进程信号、终端控制，在不同系统上差异很大。

应把平台差异隔离到小文件中：

```text
poll_linux.go
poll_darwin.go
poll_windows.go
```

并使用 build tag 控制：

```go
//go:build linux
```

跨平台库至少要在 CI 中覆盖目标平台的构建。无法运行全部测试时，也要做交叉编译或用最小 smoke test 验证文件选择和 API 形状。

## 底层优化前先测量

很多 unsafe 代码以性能为理由出现，但真正瓶颈往往在别处：算法复杂度、数据库查询、网络等待、JSON 分配、锁竞争、日志写入。

优化路径应该是：

1. 写 benchmark 或压测场景；
2. 用 pprof/trace 找热点；
3. 优先改算法、批量、缓存、分配；
4. 对比优化前后数据；
5. 只有收益显著且普通 Go 无法表达时，才考虑 unsafe。

没有数据的 unsafe 优化通常只是把代码变得不可维护。

## unsafe 代码的封装原则

如果确实需要 unsafe：

- 只放在极小包或极小函数里；
- 包注释写清楚平台假设、内存布局假设和不变量；
- 对外提供普通 Go API，不泄漏 unsafe 类型；
- 用测试覆盖边界输入、空值、不同架构假设；
- 用 benchmark 记录收益；
- 避免把 Go 内部结构当作长期协议；
- 升级 Go 版本时重点回归。

示例：不要让业务代码到处写 `unsafe.Pointer`。应该封装成：

```go
func BytesView(s string) []byte
```

然后在函数注释中明确：返回 slice 不允许修改、仅用于短期只读、依赖当前实现。即便如此，能不用就不用。

## 常见事故模式

### 把 Go 内部布局当协议

直接把结构体内存写到网络或文件，字段顺序、对齐、字节序、指针大小都会成为隐患。协议应使用显式编码，例如 `encoding/binary`、JSON、Protobuf 或自定义稳定格式。

### uintptr 保存地址

地址转成 `uintptr` 后存起来，GC 不知道它引用对象。对象可能被回收或移动，之后再转回指针就是悬空引用。

### cgo 持有 Go 指针

C 函数不能在返回后继续保存 Go 指针。否则 Go GC 和栈移动无法正确追踪。cgo 指针规则复杂，写前必须读官方文档。

### 优化破坏可读性

为了微小收益引入 unsafe，让多数维护者不敢改代码。除非数据证明收益重要，否则这是负债。

## 本章工程视角

Go 的安全默认值是生产力来源。`unsafe`、cgo 和系统调用不是炫技工具，而是不得不触碰底层边界时的最后手段。

评审底层代码时，要问：为什么普通 Go 不够？有没有 benchmark 和 profile？风险是否封装？是否依赖未承诺的运行时布局？是否跨平台验证？是否有注释解释不变量？如果这些问题回答不清，最好的选择通常是删除 unsafe，回到清晰、安全、可维护的 Go。
