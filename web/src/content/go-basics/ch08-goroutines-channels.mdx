# Goroutines 和 Channels：为每个并发任务设计生命周期

并发程序不是“让代码同时跑起来”这么简单。一个后端请求可能同时查缓存和数据库，一个 CLI 可能一边遍历文件一边汇总结果，一个爬虫可能同时访问多个页面。Go 用 goroutine 和 channel 让这些任务很容易写出来，但也因此更容易写出没人等待、没人取消、没人接收的后台工作。

这一章围绕一个小场景展开：**同时启动多个任务，收集结果，并保证调用方取消或函数返回时没有 goroutine 被遗忘**。你会从 `go` 语句、channel 发送接收、关闭、pipeline、`select`、`WaitGroup` 和并发上限一路建立工程直觉。

## 你会解决什么问题

我们从一个非常小的并发任务开始：同时查询 `cache` 和 `db`，把结果收集回来，并按稳定顺序输出。

```text
results=cache,db
```

这件小事会牵出本章大多数知识：

| 任务 | 需要的并发能力 | 工程关注点 |
|---|---|---|
| 同时启动多个查询 | `go` 语句和 goroutine | 谁负责等待它结束 |
| 收集返回值 | channel 发送和接收 | 谁会接收，发送会不会阻塞 |
| 输出稳定结果 | 排序和同步 | 并发完成顺序不等于业务顺序 |
| 处理超时和取消 | `select`、`done`、`context` | 调用方放弃后后台任务如何退出 |
| 限制并发 | buffered channel 信号量 | 不能把压力无限转嫁给下游 |

## Goroutine：由 Go runtime 调度的并发执行单元

Go 程序启动时，`main` 函数运行在 main goroutine 中。使用 `go` 语句可以启动新的 goroutine：

```go
f()    // 普通调用：等待 f 返回
go f() // 并发调用：启动新 goroutine 后立刻继续执行当前代码
```

也可以启动函数字面量：

```go
go func() {
    fmt.Println("background work")
}()
```

goroutine 很轻量，但不是免费。它仍然需要栈、调度、引用的对象、可能打开的连接和退出路径。main goroutine 返回时，整个程序会结束，其他 goroutine 不会自动把工作做完。

因此每次写 `go` 关键字，都要先问三个问题：

1. 谁等待它完成？
2. 它失败时错误发给谁？
3. 调用方取消、超时或服务关闭时，它怎样退出？

如果回答不出来，这个 goroutine 就可能泄露。泄露不一定立刻报错，但会保留内存、channel、锁、网络连接或外部请求，最终让服务越来越慢。

## Channel：goroutine 之间的通信机制

channel 是有类型的通信通道。创建一个传递 `string` 的 channel：

```go
results := make(chan string)
```

发送和接收都使用 `<-`：

```go
results <- "cache" // 发送
value := <-results  // 接收
<-results           // 接收并丢弃值
```

channel 的零值是 `nil`。对 nil channel 的发送和接收会永远阻塞；在 `select` 中，nil channel 的 case 永远不会就绪，这个特性有时可以用来动态禁用某个分支。

channel 可以关闭：

```go
close(results)
```

关闭表示“不会再发送新值”。接收方可以继续读完已经缓冲的数据；读完后再接收会得到元素零值和 `ok=false`：

```go
value, ok := <-results
if !ok {
    // channel 已关闭且没有剩余值
}
```

通常由发送方关闭 channel，因为发送方最清楚是否还有值要发送。接收方随意关闭 channel，容易让仍在发送的 goroutine 触发 `panic: send on closed channel`。

## Unbuffered channel：通信也是同步

不带容量创建的 channel 是 unbuffered channel：

```go
done := make(chan struct{})
```

发送方会阻塞，直到接收方准备好；接收方也会阻塞，直到发送方发送值。这种通信不只是传值，也建立同步关系：发送前发生的写入，对接收后的代码可见。

```go
done := make(chan struct{})

go func() {
    defer close(done)
    doWork()
}()

<-done // 等待 doWork 完成
```

当只关心“事件发生了”，不需要携带数据时，常用 `chan struct{}`。空结构体不占额外数据空间，语义也很清楚：这个 channel 传的是完成信号。

## Buffered channel：有限队列，不是无限缓冲

带缓冲 channel 在创建时指定容量：

```go
results := make(chan string, 2)
```

只要缓冲区没满，发送就可以先完成；只要缓冲区不空，接收就可以先完成。它能吸收短暂速度差，也能避免“只取最快结果”时慢 goroutine 永久卡在发送上。

```go
responses := make(chan string, 3)
go func() { responses <- request("asia") }()
go func() { responses <- request("europe") }()
go func() { responses <- request("americas") }()
return <-responses
```

但 buffered channel 不是“解决阻塞”的万能药。容量过大可能掩盖背压问题，容量过小可能仍然死锁。容量应该来自资源限制或业务约束，例如最多同时 20 个 HTTP 请求，而不是随便写一个大数字。

## Pipeline：把阶段连接起来

channel 很适合把多个阶段串成 pipeline。一个阶段输出，作为下一个阶段输入：

```go
func counter(out chan<- int) {
    defer close(out)
    for x := 0; x < 3; x++ {
        out <- x
    }
}

func squarer(out chan<- int, in <-chan int) {
    defer close(out)
    for x := range in {
        out <- x * x
    }
}
```

这里出现了单向 channel 类型：

| 类型 | 含义 | 允许操作 |
|---|---|---|
| `chan int` | 双向 channel | 发送、接收、关闭 |
| `chan<- int` | 只发送 channel | 发送、关闭 |
| `<-chan int` | 只接收 channel | 接收 |

单向类型把函数意图写进类型系统。`counter` 只负责发送，`printer` 只负责接收，编译器会阻止误用。

`range ch` 会不断接收，直到 channel 被关闭并耗尽。不是所有 channel 都必须关闭；只有当接收方需要知道“没有更多值”时，关闭才有意义。

## 并发循环：启动、等待和收集错误要成套出现

把循环改成并发很容易：

```go
for _, name := range names {
    go process(name)
}
```

这通常是不完整的，因为函数可能在 worker 完成前返回。已知任务数量时，可以用 `sync.WaitGroup` 等待所有 goroutine：

```go
var wg sync.WaitGroup
for _, name := range names {
    name := name
    wg.Add(1)
    go func() {
        defer wg.Done()
        process(name)
    }()
}
wg.Wait()
```

`wg.Add(1)` 必须在启动 goroutine 前调用，否则 `Wait` 可能在计数增加前就返回。`defer wg.Done()` 能保证错误返回时也会减少计数。

## Goroutine 泄露：提前返回也要有人排空或取消

gopl-zh 的缩略图示例展示了一个经典 bug：多个 worker 把错误发送到 channel，主 goroutine 收到第一个错误就直接返回，剩下 worker 再发送时无人接收，于是永久阻塞。

```go
errors := make(chan error)
// 如果提前 return，其他 goroutine 可能卡在 errors <- err
```

解决方向有几类：

- 使用容量足够的 buffered channel，让所有 worker 至少能发送一次结果；
- 即使提前返回，也让另一个 goroutine 继续排空 channel；
- 用 `done` 或 `context.Context` 通知 worker 停止；
- 使用 `errgroup` 统一等待、错误传播和取消。

关键不是记住某个模板，而是让每条发送路径都有接收者，让每个提前退出路径都有取消或排空策略。

## select：同时等待多个通信事件

`select` 同时等待多个 channel 操作。哪个 case 先就绪，就执行哪个；多个 case 同时就绪时，Go 会伪随机选择一个。

```go
select {
case result := <-results:
    return result, nil
case <-time.After(2 * time.Second):
    return "", fmt.Errorf("timeout")
case <-done:
    return "", fmt.Errorf("cancelled")
}
```

`select` 常用于：

- 等待结果或超时；
- 同时监听取消信号；
- 从多个输入 channel 合并事件；
- 发送时避免永久阻塞；
- 周期性 tick 和主数据流一起处理。

有 `default` 的 `select` 是非阻塞尝试：

```go
select {
case msg := <-messages:
    handle(msg)
default:
    // 暂时没有消息，继续做别的事
}
```

非阻塞操作很容易写出忙等循环。真实服务中如果没有明确需求，不要用 `default` 绕开阻塞；阻塞本身往往是背压信号。

## 取消：不能杀掉 goroutine，只能让它协作退出

Go 不能安全地从外部强行杀掉另一个 goroutine。正确方式是发出取消信号，让它在安全位置自己返回。

关闭 channel 可以广播取消：

```go
done := make(chan struct{})

select {
case out <- value:
case <-done:
    return
}
```

真实服务更常用 `context.Context`：

```go
func fetch(ctx context.Context, url string) error {
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, url, nil)
    if err != nil {
        return err
    }
    resp, err := http.DefaultClient.Do(req)
    if err != nil {
        return err
    }
    defer resp.Body.Close()
    return nil
}
```

只要函数可能阻塞、访问外部资源、跨 goroutine 工作或受请求生命周期控制，就应该考虑接收 context。context 不是普通参数袋，不要把可选业务参数塞进去；它主要用于取消、超时、deadline 和少量请求级元数据。

## 并发上限：过度并发也是 bug

并发不是越多越好。无限 goroutine 会耗尽文件描述符、数据库连接、下游 QPS、内存或调度资源。gopl-zh 的并发爬虫和目录遍历示例都使用 buffered channel 作为计数信号量限制并发：

```go
var tokens = make(chan struct{}, 20)

func crawl(url string) []string {
    tokens <- struct{}{}        // acquire
    defer func() { <-tokens }() // release
    return fetchLinks(url)
}
```

工程上要为每类资源设上限：

- HTTP 请求并发数；
- 数据库连接池；
- 队列消费者数量；
- 文件打开数量；
- CPU 密集任务 worker 数。

把本服务压力瞬间转嫁给下游，会造成级联失败。并发限制不是性能优化细节，而是生产稳定性边界。

## Goroutines 和 Channels 概念回看

| 概念 | 最小定义 | 工程判断 |
|---|---|---|
| goroutine | Go runtime 调度的并发执行单元 | 谁启动、谁等待、谁取消 |
| `go` 语句 | 并发调用函数 | main 返回前是否完成必要工作 |
| channel | 有类型的通信通道 | 谁发送、谁接收、谁关闭 |
| unbuffered channel | 发送和接收同步完成 | 是否需要强同步关系 |
| buffered channel | 有有限容量的队列 | 容量是否来自资源约束 |
| close | 宣告不会再发送 | 是否只有发送方拥有关闭权 |
| 单向 channel | `chan<- T` 或 `<-chan T` | 函数意图是否可由类型表达 |
| WaitGroup | 等待一组 goroutine 完成 | Add 是否在 go 前调用 |
| select | 同时等待多个 channel 事件 | 是否处理结果、取消和超时 |
| context | 请求级取消和 deadline 传播 | 阻塞函数是否接受 ctx |
| 信号量 | 用 buffered channel 限制并发 | 是否保护下游和本机资源 |

## 本章工程视角

goroutine 和 channel 的语法很短，但生产并发代码的检查清单很长。不要只验证“能跑通一次”。你要验证：没有人接收时发送方会怎样？接收方提前返回时发送方会怎样？第一个错误出现后其他 worker 怎样退出？客户端取消请求后后台任务是否继续访问数据库？channel 是谁关闭的？并发数有没有上限？

写并发代码时可以用这组问题自查：

- 每个 goroutine 的生命周期是否有明确所有者？
- 每条发送路径是否一定有人接收，或能被取消？
- channel 是否只由发送方关闭，且只有一个关闭者？
- WaitGroup 的 Add 是否在启动 goroutine 前执行？
- `select` 是否同时考虑结果、取消和超时？
- buffered channel 的容量是否有业务或资源依据？
- 测试是否有超时，避免 bug 让测试进程永久挂起？

能回答这些问题，goroutine 和 channel 才不是“并发魔法”，而是可维护的工程工具。
